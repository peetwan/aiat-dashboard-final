# คู่มือนักพัฒนา F2: Dashboard, data pipeline และการเผยแพร่

ฉบับภาษาอังกฤษ: [F2 developer guide](f2.md)

F2 (ฝ่าย 2) คือส่วนหนึ่งของ Dashboard สำหรับสำรวจหลักฐานเกี่ยวกับบุคคล นวัตกรรม ธุรกิจ สินทรัพย์ทางวัฒนธรรม และกิจกรรมของโครงการ ระบบรวม snapshot จากแหล่งข้อมูลแปดแหล่งเป็นตัวชี้วัดหลัก 14 ตัว และตัวชี้วัดที่เกี่ยวข้องอีกเจ็ดตัวซึ่งเรียกว่า **ตัวชี้วัดประกอบ (companions)** ผู้ใช้สำรวจผลลัพธ์ระดับประเทศ/จังหวัดที่มีข้อมูลรองรับ รวมถึงรายการ รายละเอียด และข้อจำกัดของแหล่งข้อมูลได้ ตัวชี้วัดบางตัวไม่มีผลลัพธ์เพราะหลักฐานไม่เพียงพอ นี่เป็นผลลัพธ์ที่ตั้งใจไว้ ไม่ใช่ Dashboard ที่เสีย

การพัฒนามีสองเส้นทางที่แยกจากกัน:

- **งานแอปพลิเคชัน:** เปลี่ยนวิธีที่ UI หรือ API แสดงข้อมูลที่ผ่านการตรวจทานแล้วและ commit ไว้ใต้ `data/public/f2/` งานพัฒนา UI/API ทั่วไปไม่ต้องใช้หลักฐานส่วนตัวหรือ build pipeline ใหม่ทั้งชุด
- **งานข้อมูล:** build ชุดข้อมูลภายใน (internal release) ใหม่จากหลักฐานส่วนตัวที่ตรึงเวอร์ชันไว้ ตรวจทานผลลัพธ์ และเตรียมชุดเผยแพร่สาธารณะที่ได้รับอนุญาตแยกต่างหาก การ build สำเร็จไม่ได้เปลี่ยนสิ่งที่ผู้ใช้เห็น

Pipeline ทำงานแบบ **offline** โดยอ่านไฟล์ที่จัดเตรียมไว้แทนการดึงข้อมูลจากเว็บไซต์ต้นทาง และเป็นแบบ **deterministic** กล่าวคือ เมื่อใช้โค้ด configuration และข้อมูลนำเข้าที่ตรงกันทุก byte ผลลัพธ์ต้องตรงกันทุก byte ด้วย Builder ที่รองรับจะรัน pipeline ครบทั้งกระบวนการ ไม่ใช่ checkpoint บางส่วนจากอดีต การประมวลผลครบไม่ได้หมายความว่าต้นทางครอบคลุมครบถ้วน ข้อมูลพื้นที่ที่ไม่ทราบ ตัวตนที่ยังไม่แน่นอน และข้อจำกัดของแหล่งข้อมูลยังต้องปรากฏให้เห็น

คู่มือนี้อธิบายระบบที่นำมาใช้จริง เริ่มจาก [เริ่มต้นใช้งาน](#เริ่มต้นใช้งาน) และ [สถาปัตยกรรมและตำแหน่งโค้ด](#สถาปัตยกรรมและตำแหน่งโค้ด) ส่วนหัวข้อ contract และประวัติในช่วงท้ายใช้เป็นแหล่งอ้างอิงเมื่องานของคุณต้องใช้ข้อมูลเหล่านั้น

### รัน Dashboard ปัจจุบันในเครื่อง

ใช้ Python 3.12 ขึ้นไปและ virtual environment ที่ติดตั้ง dependency ของ repository แล้ว สำหรับการตั้งค่าครั้งแรกให้ทำตาม [CONTRIBUTING: เริ่มต้นใช้งาน](../CONTRIBUTING.md#เริ่มใช้งาน) จากนั้น activate environment ใน terminal ที่จะใช้รันคำสั่ง:

```bash
# macOS/Linux (Bash or zsh)
source .venv/bin/activate
```

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

หาก code block ไม่ได้ระบุเป็นอย่างอื่น ให้รันคำสั่งจาก root ของ repository โดย activate environment นี้ไว้ คำสั่ง `python -m ...` ใช้ได้กับทั้งสอง shell ตัวอย่าง build หลายขั้นตอนในช่วงท้ายใช้ตัวแปรและ heredoc ของ **Bash** นักพัฒนา Windows ใช้ Git Bash กับ `source .venv/Scripts/activate` ได้ แทนการวาง block เหล่านั้นลงใน PowerShell

Configuration สำหรับพัฒนาโดยปริยายใช้ SQLite ในเครื่องที่ `data/runtime/dashboard.sqlite` ก่อนเริ่มให้ตรวจสอบ `.env` ที่มีอยู่และ environment override ทั้งหมด คำสั่งสำหรับพัฒนาต้องไม่ชี้ไปยังฐานข้อมูล production ค่าในเครื่องมีอธิบายไว้ใน `.env.example` และเส้นทางนี้ไม่ต้องใช้ bucket key

```bash
python -m app.cli init-db
python -m app.server
```

เปิด `http://localhost:8000` แล้วเลือก **ฝ่าย 2** ใน Dashboard เอกสารอ้างอิง API อยู่ที่ `http://localhost:8000/docs` ส่วน `http://localhost:8000/api/public/v1/f2/overview` จะแสดงภาพรวมระดับประเทศปัจจุบัน เมื่อเสร็จแล้วหยุด server ด้วย Ctrl+C

ตอนเริ่มทำงาน ระบบจะตรวจสอบชุดข้อมูลสาธารณะที่ commit ไว้และ sync ลงฐานข้อมูลในเครื่องสำหรับให้บริการ การเริ่มครั้งแรกอาจใช้เวลา แต่จะไม่ดาวน์โหลดข้อมูลต้นทางหรือ build pipeline ส่วนตัวของ F2 ใหม่ หาก validation ไม่ผ่านต้องตรวจหาสาเหตุ ห้ามข้ามขั้นตอน

สำหรับการเปลี่ยน Application ครั้งแรก ให้รัน test ที่เกี่ยวข้องซึ่งระบุใน [การตรวจสอบ](#การตรวจสอบและแก้ปัญหา) ชุด test มาตรฐานรันได้โดยไม่มีไฟล์ตรวจรับ F2 ส่วนตัว ส่วน test ที่ต้องใช้ candidate ส่วนตัวอย่างชัดเจนจะข้ามได้เมื่อไม่มีไฟล์นั้น fixture ตรวจรับสังเคราะห์สำหรับ test ใช้ทดสอบ validator เท่านั้น ไม่ใช่การอนุญาตให้เผยแพร่ข้อมูลจริง

### ขอบเขตสำคัญที่ต้องจำ

- Dashboard อ่าน **ไฟล์ข้อมูลสาธารณะที่ผ่านการตรวจทานแล้ว** ไม่ได้อ่าน response ดิบหรือตาราง candidate ส่วนตัว
- การเปลี่ยน code ของ Application ไม่ได้ให้อำนาจเปลี่ยนนิยามตัวชี้วัดหรือเผยแพร่ฟิลด์เพิ่ม
- การ build ใหม่ การตรวจทานที่ได้รับการยอมรับ การนำชุดข้อมูลมาใช้ในเครื่อง และ deployment เป็นคนละเหตุการณ์ โดยเฉพาะอย่างยิ่ง `deployment_approved=false` ในบันทึกการเตรียมชุดเผยแพร่บนเครื่อง **ไม่ใช่สวิตช์ปิด deployment** การ merge เข้า `main` อาจ trigger Railway deployment ให้ทำตาม [ขั้นตอนการเผยแพร่](publication-workflow.md)
- ใช้ feature branch และ PR สำหรับการเปลี่ยนแปลง ห้าม commit หลักฐานดิบ ไฟล์ตรวจทานส่วนตัว ฐานข้อมูลในเครื่อง หรือ secret


## สถาปัตยกรรมและตำแหน่งโค้ด

Application และ pipeline เชื่อมกันที่ไฟล์สาธารณะที่ผ่านการตรวจทานแล้ว ทั้งสองไม่ได้เชื่อมต่อเว็บไซต์ต้นทางแบบ live ให้อ่านแผนภาพนี้เป็นลำดับของผลลัพธ์และด่านตรวจทาน ไม่ใช่งานที่เกิดขึ้นในทุก web request:

```text
หลักฐานแบบแก้ไขไม่ได้ที่จัดหามาแยกต่างหาก + ข้อมูลนำเข้าประกอบการตรวจทาน/อ้างอิงที่ได้รับการยอมรับ
    -> ตรวจสอบไฟล์ในเครื่อง แหล่งข้อมูล run ขนาด และ SHA-256
    -> ระเบียนหลักฐาน ตัวตน ข้อมูลที่ต้นทางระบุ (assertion) และความสัมพันธ์ภายในแต่ละแหล่ง
    -> จับคู่ตัวตนและตรวจสอบความหมายข้ามแหล่งตามข้อสรุปที่ผ่านการตรวจทาน
    -> หน่วยที่นับในตัวชี้วัด (contribution) องค์ประกอบข้อมูลรวม และดัชนีตัวกรอง
    -> ชุดข้อมูลภายในฉบับสมบูรณ์ที่แก้ไขไม่ได้
    -> เปรียบเทียบและตรวจทานภายในโดยผูกกับ hash
    -> candidate สาธารณะแบบ deterministic + ตรวจสอบฟิลด์/ความเป็นส่วนตัวตามขอบเขต
    -> ชุดเตรียมเผยแพร่ในเครื่องที่ได้รับอนุญาตแยกต่างหากและตรวจสอบโดยอิสระ
    -> ตรวจสอบสำเนาสำหรับทดสอบการแทนที่ฉบับสมบูรณ์ และนำมาใช้ในเครื่องอย่างชัดเจน
    -> ไฟล์ข้อมูลสาธารณะที่ผ่านการตรวจทาน -> ฐานข้อมูลให้บริการ -> F2 API -> Dashboard
```

ตัวอย่างเช่น ระเบียนนวัตกรรมจากแหล่งข้อมูลจะกลายเป็นระเบียนหลักฐานจากต้นทางพร้อมตัวตนเดิมในแหล่งนั้น Pipeline จะจับคู่ระเบียนที่เข้ากันได้ (resolve) ตรวจว่านวัตกรรมเข้าเกณฑ์ K04 หรือ C04_LISTED หรือไม่ และคำนวณผลลัพธ์ จากนั้นชุดข้อมูลที่คัดเลือกเพื่อเผยแพร่ (public projection) จะเลือกเฉพาะฟิลด์ที่อนุญาต หลังผ่านการตรวจทานและนำชุดข้อมูลมาใช้แล้ว API จึงคืนรายละเอียดที่เผยแพร่นั้นและ UI นำไปแสดงได้ การแก้ UI เปลี่ยนเฉพาะขั้นตอนสุดท้าย ไม่ได้เปลี่ยนหลักฐานหรือกฎการเข้าเกณฑ์

เมื่อ Application เริ่มทำงาน ชั้นให้บริการที่ใช้ร่วมกันจะตรวจสอบและโหลดไฟล์ข้อมูลสาธารณะที่ประกาศไว้ลงฐานข้อมูล เมื่อมี request F2 จะเลือกผลลัพธ์ที่คำนวณไว้แล้วและรายละเอียดที่ต้องใช้จาก revision ที่ผ่านการตรวจทาน ทั้งสองอย่างเป็นคนละขั้นตอน การที่ API เลือกอ่านข้อมูลไม่ได้หมายความว่าการตั้งต้นฐานข้อมูลโหลดเพียง artifact เดียว

การ build จะไม่ดึงข้อมูลต้นทาง ไม่เข้าถึง R2 ไม่รัน model inference และไม่อ่านตารางอนุพันธ์เก่า การจัดหาหลักฐานเป็นอีกกระบวนการหนึ่ง ดู [การจัดเก็บหลักฐาน](evidence-storage.md) ห้ามเขียนทับหรือลบหลักฐาน canonical ใน team bucket Repository นี้เป็น Application สาธารณะสำหรับให้บริการ ไม่ใช่คลังหลักฐานดิบ

การ build ภายในไม่อ่าน frozen v2 release คำสั่ง `compare` ใช้ release นั้นเป็นข้อมูลอ้างอิงสำหรับ migration interface `project-public` ปัจจุบันยังบังคับให้มีผลการเปรียบเทียบและการตรวจทานที่ได้รับการยอมรับ จึงข้ามด่านนี้ไม่ได้แม้เป็นการ build ใหม่ตามปกติ ทั้ง v2 และข้อมูล candidate ส่วนตัวไม่ใช่ข้อมูลนำเข้าระหว่างการทำงานของเว็บ

| หน้าที่ | ไฟล์ |
|---|---|
| CLI และ interface สำหรับ build ชุดสาธารณะ | `tools/f2_pipeline/cli.py`, `release.py`, `public_projection.py` |
| การประสานงาน release ฉบับสมบูรณ์ | `tools/f2_pipeline/full_release.py` |

## ข้อมูลนำเข้าและคำศัพท์ของระบบ

### คำศัพท์และเงื่อนไขที่ระบบต้องรักษา

ในคู่มือนี้ **ผ่านการตรวจทาน (reviewed)** หมายถึงการตัดสินใจที่ใช้กับขอบเขตเฉพาะและ byte ของข้อมูลนำเข้า/ผลลัพธ์ที่ตรงกันทุกประการ ไม่ได้หมายความว่าข้อมูลทั้งหมดจากแหล่งนั้นเผยแพร่ได้อย่างปลอดภัย หรือตัวเลขนั้นเป็น KPI ที่หน่วยงานรับรองอย่างเป็นทางการ

| คำศัพท์ | ความหมาย |
|---|---|
| ตัวชี้วัด / ตัวชี้วัดหลัก (measure / headline) | ปริมาณที่มีนิยามพร้อมกฎ ได้แก่ ประชากร หน่วย ตัวกรอง และหลักฐาน ID รูปแบบ `K*` ใช้ระบุตัวชี้วัดหลักของ Dashboard โดยการแยก K01/K11 เป็นคนละ ID ทำให้มีตัวชี้วัดหลัก 14 ตัว |
| ตัวชี้วัดประกอบ (companion) | ประชากรหรือการตีความที่เกี่ยวข้องซึ่งระบุด้วย ID รูปแบบ `C*` ใช้เพิ่มบริบทให้ตัวชี้วัดหลัก ไม่ใช่จำนวนที่นำมาบวกกัน ตัวอย่างเช่น C02_COMMUNITY ไม่ใช่รายชื่อบุคคลเบื้องหลัง K02 |
| หน่วยของระเบียน (grain) | ความหมายของหนึ่งระเบียนหรือหนึ่งหน่วยที่นับ เช่น กิจกรรมหนึ่งครั้ง แทนที่จะเป็นช่วงกิจกรรมย่อย (session) ภายในกิจกรรมนั้น |
| ข้อมูลนำเข้าที่ตรึงไว้ (pinned input) / lock | ไฟล์/run ที่ระบุพร้อม hash ที่คาดไว้และเงื่อนไขตรวจสอบอื่น ๆ snapshot ที่ใหม่กว่าไม่ได้ใช้แทนได้โดยอัตโนมัติ |
| ไฟล์ข้อมูลที่ผ่านการตรวจทานสำหรับเผยแพร่ (public artifact) | ไฟล์ JSON/ข้อมูลที่ผ่านการตรวจทานและเตรียมไว้ให้บริการ ไม่ใช่ response ดิบจากต้นทาง Application อ่านเนื้อหาที่ประกาศไว้แทนการคำนวณตัวชี้วัดใหม่ |
| หัวข้อ / ขอบเขต (topic / scope) | หัวข้อรวมตัวชี้วัดหลักและตัวชี้วัดประกอบที่เกี่ยวข้อง ขอบเขตคือการเลือกที่ระบบรองรับสำหรับหนึ่งผลลัพธ์ เช่น ระดับประเทศหรือจังหวัดหนึ่งจังหวัด |
| การอนุญาตให้แสดงในข้อมูลสาธารณะ (public admission) | สิทธิ์ให้เอนทิตีหรือฟิลด์ที่ถูกนับปรากฏในชุดข้อมูลที่คัดเลือกเพื่อเผยแพร่ เอนทิตีอาจถูกนับในยอดรวมได้แม้งดเผยแพร่รายละเอียดที่ไม่ปลอดภัยไว้ |
| กลุ่มสินค้า/บริการ (offering family) | สินค้า/บริการ (offering) และรุ่นย่อย (variant) ที่เกี่ยวข้องซึ่งรวมเป็นหนึ่งหน่วยนับของ K07 ราคาและระเบียนประกอบของแต่ละรายการยังคงแยกกัน |
| ไฟล์รายละเอียดแยกย่อย (detail shard) | ไฟล์ย่อยที่จำกัดขนาดและมีรายละเอียดบางส่วนของหัวข้อ ต้องใช้ lookup ที่ประกาศไว้เพื่อหารายละเอียดของเอนทิตี ห้ามเดาจากชื่อไฟล์ |
| ระเบียนหลักฐานจากต้นทาง (observation) | ระเบียนหรือ assertion หนึ่งรายการที่เก็บมาจากต้นทาง ระเบียนหลักฐานที่ซ้ำกันไม่จำเป็นต้องเป็นคนละเอนทิตี |
| ตัวตนภายในแหล่งข้อมูล (source-local identity) | เอนทิตีที่ระบุได้ภายในแหล่งและ dataset หนึ่ง เช่น นวัตกรรม ID ตัวเลขเดียวกันใน dataset อื่นไม่จำเป็นต้องหมายถึงสิ่งเดียวกัน |
| ตัวตนรวม (global identity) | identity ที่ได้จากกฎจับคู่ระเบียนซึ่งผ่านการตรวจทาน และเชื่อมสมาชิกจากแต่ละแหล่งที่เข้ากันได้ ไม่ใช่คำสั่งให้รวมทุกชื่อที่คล้ายกัน |
| ข้อมูลที่ต้นทางระบุ / ความสัมพันธ์ (assertion / relationship) | ข้อมูลหรือความเชื่อมโยงที่มีต้นทางรองรับ โดยระบุชัดว่าเกี่ยวกับเอนทิตีใด ในบทบาทใด และมาจากระเบียนหลักฐานใด |
| การเข้าเกณฑ์ (eligibility) | คุณสมบัติที่จะนับในตัวชี้วัดหนึ่ง ซึ่งแยกจากตัวตน |
| หน่วยที่นับในตัวชี้วัด (contribution) | หนึ่งหน่วยนับที่มี key เฉพาะเป็น `(measure_id, entity_id)` |
| ความเชื่อมโยงสำหรับกรอง (membership) | ความเชื่อมโยงกับพื้นที่/หมวดหมู่ที่มีหลักฐานรองรับ ซึ่งใช้กรอง contribution |
| องค์ประกอบข้อมูลรวม (aggregate component) | จำนวนที่แหล่งข้อมูลรายงาน พร้อมหน่วย ตัวหาร และกลุ่มที่ใช้แจกแจงข้อมูล (breakdown group) เป็นข้อมูลสรุป ไม่ใช่รายชื่อบุคคลหรือธุรกิจแต่ละราย |
| ข้อมูลสรุปแยกทีละมิติ (marginal breakdown) | ข้อมูลสรุปที่จัดกลุ่มทีละหนึ่งมิติ ยอดรวมที่แยกตามประเภทธุรกิจกับยอดรวมที่แยกตามจังหวัดไม่ได้ให้ตารางไขว้ประเภทธุรกิจกับจังหวัด (cross-tab) |
| ชุดข้อมูลภายใน (internal release) | ชุดตรวจสอบย้อนหลังส่วนตัวที่ครบถ้วน ได้แก่ ตารางที่ normalize แล้ว ตัวตน การคำนวณ ลิงก์หลักฐาน และผล validation |
| ชุดข้อมูลที่คัดเลือกเพื่อเผยแพร่ (public projection) / ชุดข้อมูลรอตรวจทาน (stage) | ฟิลด์และผลลัพธ์ที่เลือกและเตรียมไว้ให้ตรวจทานก่อนเผยแพร่ stage คือ directory ของ candidate ไม่ใช่ไฟล์ที่ Application ให้บริการอยู่ในปัจจุบัน |
| การเตรียมชุดเผยแพร่บนเครื่อง (local promotion) / การนำชุดข้อมูลมาใช้ (activation) | Promotion สร้างชุดเผยแพร่ที่ตรวจสอบแล้วและได้รับอนุญาตแยกต่างหาก ส่วน activation นำชุดนั้นไปใช้กับไฟล์ให้บริการในเครื่อง ทั้งสองอย่างไม่ใช่การ merge Git หรือ deployment |
| สำเนาสำหรับทดสอบการแทนที่ (replacement overlay) | สำเนาชั่วคราวของชุดเผยแพร่ทั้งหมด ซึ่งใส่ชุด F2 ที่เสนอให้แทนที่ลงไป ใช้ตรวจว่า F2 และข้อมูลเดิมที่ไม่ใช่ F2 ยังทำงานร่วมกันได้อย่างถูกต้อง |
| Manifest / contract / receipt | Manifest อธิบาย package หรือรายการข้อมูลที่ให้บริการ contract กำหนดผลลัพธ์ที่อนุญาตและกฎ validation ส่วน receipt ผูกผลลัพธ์สาธารณะครบทั้งชุดเข้ากับ hash ดู [ขั้นตอนการเผยแพร่](publication-workflow.md#manifest-กับ-receipt-ต่างกันอย่างไร) |

ตัวอย่างเช่น **ตัวชี้วัดหลัก 14 ตัว** ไม่ได้เท่ากับ **dataset อิสระ 14 ชุด** หนึ่งหัวข้ออาจมีตัวชี้วัดหลักและตัวชี้วัดประกอบซึ่งมีเอนทิตีบางส่วนร่วมกัน แต่ตอบคำถามต่างกัน หน้ารายการเป็นเพียงอีกมุมมองหนึ่ง การกรอง label ในหน้านั้นไม่เปลี่ยนยอดรวมของตัวชี้วัดที่ผ่านการตรวจทานแล้ว

การรวมตัวตนต้องรักษาระเบียนหลักฐาน บทบาท ตำแหน่งที่ตั้ง ผลประเมิน และข้อขัดแย้งทั้งหมดไว้ `match` เชื่อมตัวตนที่เข้ากันได้ `keep_separate` บันทึกว่าต้องแยกจากกัน และ `unresolved` หมายถึงยังไม่มีข้อยุติ การเชื่อมต่อกันเป็นทอด ๆ จากการ match ต้องไม่ลบล้าง cannot-link (การตัดสินใจว่า “ห้ามรวม” อย่างชัดเจน) หรือข้อห้ามที่รักษาสถานะ unresolved ไว้ การอยู่ในโครงการเดียวกันไม่ทำให้บุคคลมีบทบาทเดียวกัน การจับคู่ธุรกิจไม่ได้ทำให้สินค้าทั้งหมดรวมเป็นรายการเดียว และห้ามนำตำแหน่งสินค้ามาถือเป็นตำแหน่งผู้ขาย

ตัวชี้หลักฐานต้องชี้ไปยังระเบียนที่รองรับข้อมูลนั้นจริง ไม่ใช่เพียงแถวที่มีอยู่ในไฟล์เดียวกัน ID ตัวเลขภายในแต่ละ dataset ใช้แทนกันไม่ได้ เจ้าของรายการความต้องการ (requirement) ของ MRU ต้องไม่ถูกเชื่อมกับนวัตกรรมเพียงเพราะสอง dataset ใช้ ID เดียวกัน ก่อนยอมรับผลลัพธ์ที่คำนวณขึ้น ระบบจะตรวจ identity และความเป็นเจ้าของของ requirement กับระเบียนย่อยของ MRU, จำนวนแถวที่ RINMP ประกาศและรหัสเจ้าของ ตลอดจนความเป็นเจ้าของระหว่าง profile กับ observation ของ RINMP

| ไฟล์ภูมิศาสตร์/ข้อมูลอ้างอิง และข้อมูลนำเข้าสำหรับตรวจทานส่วนตัว | ใช้ path/hash ที่ประกาศใน configuration สำหรับ build ที่เลือกและ lock ของ configuration นั้น ขอ package ที่ตรงกันจากผู้ดูแล release ที่ได้รับการยอมรับนั้น |
| ข้อมูลอ้างอิง frozen v2 สำหรับเปรียบเทียบ | ขอ directory `f2-dashboard-snapshot-v2` ที่ตรวจสอบแล้วพร้อม manifest ข้อมูลนี้จำเป็นสำหรับการเปรียบเทียบ แต่ไม่จำเป็นต่อการรัน Dashboard |
| บันทึกตรวจรับฟิลด์/ภูมิศาสตร์ | ขอบันทึกที่ตรงกับ configuration ทุกประการ รวมถึงรายการใต้ `checkpoints/` ห้ามแทนที่ด้วย test fixture หรือ status flag ที่เพิ่งเขียนขึ้น |

เครื่องมือดึงหลักฐานทั่วไปจะเขียนข้อมูลลง `<AIAT_EVIDENCE_ROOT>/data/raw/<source_id>/<run_id>/` แต่ runbook นี้ส่ง `data/runtime/f2/raw` ให้ builder จัดให้ไฟล์ที่ประกาศไว้เข้าถึงได้ใต้ `--evidence-root` ที่เลือก อย่าคิดว่าการดาวน์โหลด run จะติดตั้งข้อมูลอ้างอิง/ข้อมูลตรวจทานของ F2 ทั้งหมดด้วย ตรวจ layout ที่ lock คาดไว้ก่อน build

ห้าม commit ข้อมูลนำเข้าส่วนตัวหรือคัดลอก external workspace ทั้งชุดเข้ามาใน repository นี้ `--review-root .` ทำให้ path ที่ประกาศไว้ resolve โดยอิงจาก root ของ repository รวมถึง `checkpoints/` ไม่ได้หมายความว่า “อ่านเฉพาะ directory `reviews/`” หากไม่ทราบข้อมูลนำเข้าที่จำเป็นหรือผู้ดูแล ให้หยุดและสอบถามทีมแทนการสร้างการอนุมัติขึ้นใหม่จากคู่มือนี้

ไม่มีข้อมูลนำเข้ารายการใดเลือก “latest” โดยปริยาย ไฟล์ที่หายไป เกินมา ซ้ำ เก่า หรือไม่ตรงกันจะทำให้ validation ไม่ผ่าน สำเนาแบบบีบอัดและแบบขยายต้องตรงกัน เก็บข้อยกเว้น manifest hash ของ Learning Dashboard ที่บันทึกไว้ให้ชัดเจน พร้อม hash เดิม hash จริงที่ตรึงไว้ เหตุผล และข้อมูลอ้างอิงการยอมรับ ห้ามเขียน source manifest ใหม่หรือปิดการตรวจสอบ

AtLocal และ iCommunity มีโหมดเผยแพร่ `snapshot_only` ที่ได้รับการยอมรับ โดยมี `cloud_policy=team_approved_public` และอนุญาตให้ใช้ค่าข้อมูลใน production ได้ ตรวจ catalog ที่สร้างขึ้นก่อนเผยแพร่ การตรวจทานความหมายยังแยกจากสิทธิ์ในการเผยแพร่ ให้แก้ source card/registry ใน canonical evidence workspace แล้วสร้าง catalog ใหม่แทนการแก้ `config/source_catalog.json` ด้วยมือ

`f2_icommunity` ยังคงเป็น canonical bundle เดียว โดย `icommunity.in.th` เป็น portal และ `apptechpmua.com` เป็นระบบสนับสนุน ทุก observation เก็บ provenance ของ dataset และระบบต้นทางไว้ ห้ามแยก bundle นี้หรือนับระบบสนับสนุนซ้ำเป็นแหล่งที่สอง Wallet All และ Wallet Cluster ไม่ใช่ข้อมูลนำเข้าของ release นี้ จึงไม่ให้ข้อมูล K10 และไม่ใช้ยืนยัน cluster ของ K11

กฎด้านความหมายที่ต้องใช้:

- ไม่มีตัวกรองปี/เดือนปฏิทินหรือ time series ที่แต่งขึ้น ปีงบประมาณ/ปีโครงการเป็นเพียงบริบท เวลาที่เก็บข้อมูลไม่ใช่วันที่ราคาเริ่มมีผลหรือหลักฐานว่ายังมีให้ใช้ในปัจจุบัน
- ใช้ทั้ง `supported_filters` และ `permitted_combinations` ของตัวชี้วัดที่เลือก ตัวชี้วัดประกอบอาจต่างจากตัวชี้วัดหลัก ให้เตรียมชุดผลลัพธ์ระดับประเทศและครบทั้ง 77 จังหวัด รวมถึงผลที่ระบุชัดว่าไม่มีข้อมูลให้แสดง (unavailable)
- นับเอนทิตีไม่ซ้ำหลัง join ภายในระบบ หลายค่าในมิติเดียวที่รองรับจะรวมแบบ union ส่วนต่างมิติใช้ intersection UI เลือกได้ระดับประเทศหรือหนึ่งจังหวัด ไม่ใช่ข้อกำหนดที่อนุญาตให้เลือกหลายค่าได้ทั่วไปตามที่ตีความขึ้นเอง
- รายการที่ไม่ทราบพื้นที่ยังอยู่เฉพาะระดับประเทศ ส่วน membership หลายจังหวัดที่ซ้อนกันนำมาบวกกันไม่ได้ ห้ามรวมจำนวนรายจังหวัดเพื่อสร้างผลระดับประเทศขึ้นใหม่
- ค่าศูนย์ (zero), ไม่ทราบ (unknown), ข้อมูลขาดหาย (missing) และไม่มีข้อมูลให้ใช้ในขอบเขตนั้น (unavailable) มีความหมายต่างกัน การเลือกเอนทิตีในขอบเขตที่รองรับแต่ได้ผลว่างอาจหมายถึงไม่มีระเบียนเข้าเกณฑ์ใน snapshot นี้ ส่วนสมาชิกข้อมูลรวมที่ขาดหาย ข้อมูลนำเข้าที่ใช้ไม่ได้ และตัวกรองที่ไม่รองรับไม่ใช่ศูนย์
- คำขอข้อมูลจังหวัดที่ไม่รองรับต้องไม่คืนยอดระดับประเทศหรือภาคโดยไม่แจ้ง ข้อมูลประกอบในขอบเขตที่กว้างกว่า (หากมี) ต้องแยกป้ายกำกับและขอบเขตให้ชัดเจน
- การแบ่งภาคของแหล่ง Learning ใช้นิยามคนละชุดกับภาคของ Dashboard ชื่อที่เหมือนกันไม่ได้ยืนยันว่าขอบเขตเท่ากัน
- การ query ข้อมูลรวมทำงานภายใน breakdown group ที่ใช้ได้หนึ่งกลุ่ม โดยใช้จำนวน/ตัวหารที่ประกาศไว้ ข้อมูลสรุปธุรกิจที่แยกอิสระสี่มิติของ Learning ไม่ได้กลายเป็นธุรกิจ 1,500 ราย ยอดที่ K02 รายงานกับกลุ่มพื้นที่ไม่จำเป็นต้องตรงกัน ห้ามสร้างบุคคลขึ้นเพื่อเติมส่วนต่าง
- ข้อมูลเงินใช้เลขทศนิยม การปัดเพื่อแสดงผลไม่เปลี่ยนจำนวนที่เก็บไว้ จำนวนจากการค้นหา/แบ่งหน้าไม่ใช้คำนวณ KPI ใหม่

สองตัวอย่างต่อไปนี้ช่วยให้ใช้กฎได้ง่ายขึ้น:

- หากบุคคลที่ได้รับการยอมรับหนึ่งคนมี membership ที่รองรับในสองจังหวัด แต่ละจังหวัดนับบุคคลนั้นได้หนึ่งครั้ง ส่วนผลระดับประเทศนับรวมเพียงครั้งเดียว การบวกผลรายจังหวัดจะทำให้นับซ้ำ
- หากแหล่งข้อมูลรายงานธุรกิจ 375 รายโดยแยกเป็นสี่มิติ ข้อมูลเหล่านั้นคือสี่มุมมองของประชากร ไม่ใช่ธุรกิจ 1,500 ราย และยังมีหลักฐานไม่พอสำหรับ cross-tab รวม ให้ใช้เฉพาะ breakdown ที่ประกาศไว้สำหรับ query นั้น

## ขั้นตอน build และตรวจทาน

ใช้ runbook นี้เมื่อสร้างหรือเปลี่ยน dataset จริง ไม่ใช่สำหรับการเปลี่ยน UI ทั่วไป เริ่มจากขอ [ข้อมูลนำเข้าส่วนตัวที่ประกาศไว้](#ชุดแหล่งข้อมูลที่ตรึงไว้) เครื่องมือปัจจุบันยังบังคับให้เปรียบเทียบกับ frozen v2 ก่อนสร้างชุดข้อมูลที่คัดเลือกเพื่อเผยแพร่ แม้เป็นการ build ใหม่ตามปกติ นี่เป็นข้อจำกัดของ implementation ไม่ใช่ข้อกำหนดให้สร้างยอดรวมของ v2 ซ้ำ

### การส่งมอบระหว่างการตรวจทาน

ก่อนเริ่มงานเผยแพร่ ให้ตกลงกับผู้ดูแล F2 ว่าใครรับผิดชอบการตัดสินใจต่อไปนี้ Repository ไม่ได้ระบุชื่อผู้ดำรงบทบาทอนุมัติข้อมูลเหล่านี้ และสิทธิ์เขียน GitHub เพียงอย่างเดียวไม่ใช่สิทธิ์เผยแพร่ ใช้ข้อมูลติดต่อทีมใน [CONTRIBUTING](../CONTRIBUTING.md) / [CODEOWNERS](../.github/CODEOWNERS) เพื่อหาผู้ตรวจทานหรือผู้รับผิดชอบการอนุมัติ (owner)

| จุดส่งมอบ | สิ่งที่นักพัฒนาส่งให้ | ผลลัพธ์ที่ต้องมีก่อนดำเนินการต่อ |
|---|---|---|
| ความพร้อมของข้อมูลนำเข้า | Configuration ที่เลือก รายการ run/ไฟล์ที่ lock แล้ว และข้อยกเว้นด้าน integrity | ผู้ดูแลหลักฐานจัดหาไฟล์และบันทึกตรวจทาน/อ้างอิงที่ตรงกัน ข้อมูลนำเข้าที่ขาดจะหยุดการ build จริง |
| การตรวจรับภายใน | Release ที่แก้ไขไม่ได้ ผลเปรียบเทียบกับ v2 และคำอธิบายความต่างที่มีนัยสำคัญทุกรายการ | ผู้ตรวจทานที่มีอำนาจบันทึกการยอมรับ hash ที่ตรงกันและความต่างแต่ละรายการ ขอบเขตนี้ครอบคลุมเฉพาะผลลัพธ์ภายใน |
| การตรวจทานฟิลด์สาธารณะ/ความเป็นส่วนตัว/ความหมาย | Stage สาธารณะและ contract ที่เสนอ การเปลี่ยนฟิลด์ จำนวน เหตุผลที่งดเผยแพร่ฟิลด์ และผล validation | ผู้ตรวจทาน/ผู้รับผิดชอบการอนุมัติยืนยันขอบเขตสาธารณะที่ต้องการและจัดทำบันทึกตรวจรับที่ผูกกับข้อมูลตามที่กำหนด ขอบเขตใหม่ต้องมี policy/configuration revision ที่ผ่านการตรวจทาน |
| การเตรียมชุดเผยแพร่และนำมาใช้ในเครื่อง | Stage ที่ได้รับการยอมรับ หลักฐานการตรวจทาน ผลการตรวจสอบ และแผนรักษาข้อมูล | ผู้รับผิดชอบการอนุมัติอนุญาตการเผยแพร่บนเครื่องและการแทนที่ชุดนั้นอย่างชัดเจน การผ่าน validator ไม่ใช่การอนุญาต |
| การ merge repository และ deployment | PR ที่มีเฉพาะการเปลี่ยน code/data ซึ่งตั้งใจไว้และผ่านการตรวจทาน พร้อมผลการตรวจ | ทำตามการตรวจสอบ/การตรวจทานและกฎ merge ของ repository Railway deployment เป็นผลอีกขั้นหนึ่งจากการ merge เข้า `main` |

หากการตรวจทานเปลี่ยนข้อมูลนำเข้า นิยาม หรือ policy ให้ build candidate ใหม่และทำขั้นตอนตรวจที่ได้รับผลกระทบซ้ำ ห้าม patch candidate ที่แก้ไขไม่ได้หรือใช้การยอมรับเดิมต่อเมื่อ hash ไม่ตรงแล้ว

### 1. เตรียมข้อมูลนำเข้าที่ประกาศไว้และ path ผลลัพธ์ใหม่

รัน block ต่อไปนี้ใน Bash จาก root ของ repository โดย activate virtual environment แล้ว เลือก tag ใหม่ directory ผลลัพธ์ทั้งหมดของ builder ต้องยังไม่มีอยู่ ห้ามใช้ directory ที่ได้รับการยอมรับแล้วซ้ำหรือให้ทับซ้อนกับข้อมูลนำเข้าหลักฐาน/การตรวจทาน ตัวอย่างนี้สร้าง candidate ไม่ใช่ข้อมูลที่ให้บริการ

```bash
TAG="f2-next-review"
CONFIG="config/f2_pipeline/v3-c08-identity-review-v1.json"
RELEASE="data/runtime/f2/releases/$TAG"
COMPARISON_DIR="data/runtime/f2/comparisons/$TAG"
COMPARISON_REVIEW="$COMPARISON_DIR/accepted-review.json"
STAGE="data/runtime/f2/public-projections/$TAG"
CONTRACT="$COMPARISON_DIR/staged-contract.json"
BUNDLE="data/runtime/f2/promotions/$TAG"
```

Tag ใช้แยกตำแหน่งผลลัพธ์ ไม่ได้สร้างการอนุมัติหรือเปลี่ยน logical release identity ของ configuration หากหลักฐาน นิยาม หรือขอบเขตฟิลด์เปลี่ยน ให้เตรียม configuration เวอร์ชันใหม่และตรวจทาน dependency แทนการแก้ configuration ที่ lock ไว้แล้ว

การ audit ข้อมูลนำเข้า (ทำหรือไม่ก็ได้):

```bash
python -m tools.f2_pipeline audit-inputs \
  --lock config/f2_pipeline/inputs.v3.json \
  --evidence-root data/runtime/f2/raw --review-root .
```

`audit-inputs` ตรวจหลักฐานและทะเบียนการตรวจทานที่ย้ายมาแล้วในรูปแบบที่เครื่องมือรองรับ แต่ไม่ใช้แทนการ build เต็มรูปแบบตาม configuration และการตรวจกฎของแต่ละโดเมน

### 2. Build ชุดข้อมูลภายในฉบับสมบูรณ์

```bash
python -m tools.f2_pipeline build \
  --config "$CONFIG" \
  --evidence-root data/runtime/f2/raw \
  --review-root . \
  --output "$RELEASE"
```

ระบบยอมรับเฉพาะ configuration ที่มี `profile=full`, `complete=true`, `publication_status=internal_only` ห้ามพยายาม build checkpoint เก่าที่มีเฉพาะ K12, identity, commerce หรือ aggregate

เมื่อ build สำเร็จ โปรแกรมจะจบด้วย exit code 0 และเขียนชุดข้อมูลภายในฉบับสมบูรณ์ไว้ที่ `$RELEASE` โดย manifest ระบุ `validation_status=passed` และ `publication_status=internal_only` นี่หมายถึง build สำเร็จ ไม่ใช่ผ่านการตรวจรับ

ใช้ไฟล์ต่อไปนี้ตรวจผลลัพธ์:

| ไฟล์ | วัตถุประสงค์ |
|---|---|
| `manifest.json`, `input_manifest.csv`, `review_input_audit.json` | Hash ของผลลัพธ์ และหลักฐาน configuration code และข้อมูลนำเข้าสำหรับตรวจทานที่ใช้จริง |
| `definitions.json`, `projection_policy.json`, `measure_dictionary.csv` | ความหมายของตัวชี้วัดและ policy การเลือกฟิลด์สาธารณะ |
| `results.json`, `kpi_results.csv`, `companion_results.csv` | ผลลัพธ์ตัวชี้วัดหลัก/ตัวชี้วัดประกอบที่คำนวณแล้ว |
| `entity_contributions.csv`, `evidence_links.csv`, `eligibility_evidence.csv` | สิ่งที่ถูกนับ เหตุผลที่เข้าเกณฑ์ และหลักฐานประกอบ |
| `province_memberships.csv`, `province_coverage.csv`, `category_memberships.csv`, `aggregate_breakdowns.csv` | Membership ของตัวกรอง ความครอบคลุม และองค์ประกอบข้อมูลรวม |
| `validation_checks.csv`, `table_catalog.csv`, `sources/`, `domains/` | ผลการตรวจสอบ, schema ของตาราง และตารางต้นทาง/domain ที่ normalize แล้ว |

ระบบตรวจทุกไฟล์ แถว key และ JSON cell ตัวตนและลำดับผลลัพธ์ต้องเป็น deterministic

ตรวจการเลือกข้อมูลภายในได้โดยไม่เปลี่ยน release:

```bash
python -m tools.f2_pipeline query \
  --release "$RELEASE" --measure K12 --filters '{}'
```

Query ภายในใช้คำศัพท์ตัวกรองที่ประกาศไว้ของตัวเอง ชื่อ HTTP parameter มีเอกสารแยกไว้ด้านล่าง ห้ามแก้ตารางผลลัพธ์เพื่อให้ได้ยอดรวมที่ต้องการ

### 3. เปรียบเทียบและขอการตรวจรับภายใน

ตั้ง `V2_REFERENCE` ให้ชี้ไปยัง directory `f2-dashboard-snapshot-v2` ที่ตรวจสอบแล้วและได้รับจากผู้ดูแล release เช่น ใช้ `V2_REFERENCE="/path/to/verified/f2-dashboard-snapshot-v2"` หลังเปลี่ยน placeholder นั้น ข้อมูลนี้ไม่มีใน clean clone และไม่จำเป็นต่อการรัน Dashboard

```bash
python -m tools.f2_pipeline compare \
  --release "$RELEASE" \
  --reference "$V2_REFERENCE" \
  --output "$COMPARISON_DIR"
```

เมื่อสำเร็จจะเขียน `$COMPARISON_DIR/comparison.json` และหลักฐานเปรียบเทียบที่เกี่ยวข้อง โดย `review_status` เป็น `pending_review` ส่ง release และผลเปรียบเทียบให้ผู้ตรวจทานที่ตกลงไว้ผ่านพื้นที่ตรวจทานส่วนตัวที่ทีมอนุญาต ห้ามแนบกับ PR สาธารณะหรือวางแถวข้อมูลส่วนตัวลงไป ห้ามสร้างชุดข้อมูลที่คัดเลือกเพื่อเผยแพร่ต่อจนกว่าจะมีบันทึกการยอมรับที่ตรงกัน

ตรวจทานค่า นิยาม ตัวตน การเข้าเกณฑ์ ข้อมูลพื้นที่ องค์ประกอบข้อมูลรวม ตารางรายละเอียด และความต่างเชิงความหมาย ไม่ใช่ดูเพียงว่ายอดตัวชี้วัดหลักเท่ากันหรือไม่ ห้ามบังคับผลปัจจุบันให้ตรงกับ v2 manifest ของ frozen v2 บันทึกความต่างของ source code ไว้ ชุดนั้นเป็น artifact สำหรับเปรียบเทียบ ไม่ใช่ข้อมูลนำเข้าสำหรับ build ซ้ำด้วยโค้ดปัจจุบันให้ได้ผลเดิม

ผู้ตรวจทานต้องบันทึกการตัดสินใจจริงลง `$COMPARISON_REVIEW` นักพัฒนาเตรียมหลักฐานได้แต่ห้ามสร้างการยอมรับขึ้นเพื่อปลดล็อกคำสั่ง บันทึกนี้ประกอบด้วย release ID, hash สามรายการด้านล่าง, status/ขอบเขตการตรวจทาน และรายการ `decisions` โดย `comparison_review.py:verify_comparison_review` บังคับเงื่อนไขดังนี้:

- `schema_version=1`, `release_id` ต้องตรงกัน, `review_status=accepted` และ `scope=internal_release_only`;
- `release_manifest_sha256`, `comparison_sha256` และ `reference_manifest_sha256` ต้องตรงทุกประการ;
- ความต่างที่มีนัยสำคัญแต่ละ `difference_id` ต้องมี decision ที่ accepted ตรงหนึ่งรายการ พร้อม `reason` และ `acceptance_basis` ที่ไม่ว่าง;
- หลักฐานเปรียบเทียบต้องสอดคล้องกับ release ปัจจุบัน

ไม่มีคำสั่ง CLI ที่ให้การยอมรับโดยอัตโนมัติ การตัดสินใจเก่านำมาใช้ต่อได้เฉพาะส่วนที่หลักฐานยังใช้ได้ โดยต้องผูกกับ byte ชุดใหม่ การที่ยอด KPI ไม่เปลี่ยนเพียงอย่างเดียวยังไม่พอ การตรวจรับภายในไม่ใช่การอนุมัติฟิลด์สาธารณะหรือ local promotion

### 4. สร้าง candidate สาธารณะและเตรียม contract

```bash
python -m tools.f2_pipeline project-public \
  --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --output "$STAGE"
```

ผลลัพธ์มีสถานะ `staged_for_review` ไม่ใช่พร้อมเผยแพร่ ระบบเลือกฟิลด์จากชุดข้อมูลภายในตาม policy ที่ lock ไว้ และไม่เขียนลง `data/public/`

ไม่มีคำสั่ง CLI เฉพาะสำหรับสร้าง staged contract ตัวอย่าง Python ต่อไปนี้เรียก `make_staged_contract` และสร้าง `$CONTRACT` เป็นไฟล์ใหม่เท่านั้น หากไฟล์มีอยู่แล้วจะไม่เขียนทับ ไม่ได้แทน contract ที่ใช้งานอยู่หรืออนุมัติฟิลด์/จำนวนที่เปลี่ยนไป ตัวอย่างนี้อ่านเฉพาะ candidate และชุดข้อมูลภายในของ candidate

```bash
python - "$STAGE" "$RELEASE" "$CONTRACT" <<'PY'
import sys
from pathlib import Path
from tools.f2_pipeline.common import canonical_json, load_json
from tools.f2_pipeline.public_stage import make_staged_contract

stage, release, destination = map(Path, sys.argv[1:])
contract = make_staged_contract(
    stage,
    load_json(release / "definitions.json")["measures"],
    load_json(release / "projection_policy.json"),
)
with destination.open("x", encoding="utf-8", newline="\n") as stream:
    stream.write(canonical_json(contract) + "\n")
PY
```

ตรวจ contract ของ candidate เทียบกับ contract เดิมและ policy ที่อนุมัติแล้ว การเปลี่ยนจำนวน identity, field context, รายการผลลัพธ์ หรือ limit เป็นการเปลี่ยนแปลงที่ต้องตรวจทาน ไม่ใช่ refresh ที่อนุมัติโดยอัตโนมัติ เก็บ contract ที่สร้างขึ้นไว้กับหลักฐานของ candidate

### 5. ตรวจสอบ stage โดยไม่กระทบชุดเผยแพร่ที่ใช้งานอยู่

F2 เปิดใช้งานอยู่แล้วใน repository นี้ คำสั่งรวม `validate-public-stage` แบบปริยายจงใจปฏิเสธ repository ที่มี `data/public/f2/` และจะไม่แทนที่โดยปริยาย ใช้โหมด F2-only เพื่อตรวจวินิจฉัย:

```bash
python -m tools.f2_pipeline validate-public-stage \
  --stage "$STAGE" --contract "$CONTRACT" \
  --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --f2-only
```

คำสั่งจะ build stage ใหม่จากข้อมูลนำเข้าที่ส่งให้ ตรวจว่าไฟล์และ contract ตรงกันทุกประการ และรัน publication validation ในพื้นที่ชั่วคราว ผลที่คาดคือ `status=valid`, `validation_scope=staged_only` และ `active_files_modified=false` **ขั้นตอนนี้ตรวจ F2 แยกเดี่ยว ไม่ได้ยืนยันว่า workspace สำหรับแทนที่ทั้งชุดอยู่ในเพดานขนาดข้อมูลหรือพร้อมนำมาใช้**

หากนำ F2 มาใช้ครั้งแรกใน repository ที่ยังไม่มีชุดเผยแพร่ F2 ให้ละ `--f2-only` โดย `--repository` ชี้ไปยัง repository ชั่วคราวที่เตรียมไว้ได้ หากเป็นการ refresh ชุดเผยแพร่ปัจจุบัน ให้ทำตามขั้นตอน replacement overlay ด้านล่าง ห้ามลบไฟล์ F2 ที่ active อยู่เพียงเพื่อให้ stage validation ผ่าน

### 6. อนุญาตและตรวจสอบการเตรียมชุดเผยแพร่บนเครื่องแยกต่างหาก

หลังผ่านการตรวจทานฟิลด์/ความเป็นส่วนตัว/ความหมาย และมีการอนุญาต local promotion อย่างชัดเจนแล้วเท่านั้น จึงตั้ง `DECISION` ให้ชี้ไปยังไฟล์ JSON การตัดสินใจที่ผ่านการตรวจทานจากผู้รับผิดชอบการอนุมัติ ไฟล์นี้เป็นคนละไฟล์และคนละขอบเขตกับ `$COMPARISON_REVIEW` ห้ามสร้างจากคำสั่งด้านล่าง

```bash
python -m tools.f2_pipeline promote-local \
  --stage "$STAGE" --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --decision "$DECISION" --output "$BUNDLE"

python -m tools.f2_pipeline verify-local-promotion \
  --bundle "$BUNDLE" --stage "$STAGE" --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --decision "$DECISION"
```

Decision มีแปดฟิลด์พอดี ได้แก่ `schema_version`, `decision_id`, `decision_status`, `release_id`, `source_stage_manifest_sha256`, `scope`, `local_publication_approved` และ `deployment_approved` โดย `promotion.py:_validate_decision` เป็นแหล่งอ้างอิง implementation ระบบกำหนดให้ schema version เป็น 1, decision ต้อง accepted สำหรับ release ที่รองรับ, stage-manifest SHA-256 ต้องตรงทุกประการ, `scope=local_publication_only`, `local_publication_approved=true` และ `deployment_approved=false`

Decision ID ที่รองรับปัจจุบันคือ `f2-local-promotion-v1`, `f2-c02-province-local-promotion-v1` และ `f2-c02-map-local-promotion-v1` ค่าเหล่านี้เป็น identifier ของ protocol ไม่ใช่วิธีอนุมัติตัวเอง หากขอบเขตการตัดสินใจใหม่ยังไม่รองรับ ให้ตกลงการเปลี่ยน contract กับผู้รับผิดชอบการอนุมัติ แทนการเลือก ID ที่ไม่เกี่ยวข้องเพื่อให้ validation ผ่าน การคัดลอก decision เก่าที่ hash ไม่เป็นปัจจุบันใช้ไม่ได้ ระบบเชื่อถือบันทึกตรวจทานบนเครื่องนี้ แต่ไม่ได้ตรวจยืนยันตัวตนด้วยวิธีทางวิทยาการเข้ารหัส (cryptographic identity check) และบันทึกนี้ใช้แทนการอนุญาตจากผู้รับผิดชอบไม่ได้

ทั้งสองคำสั่งต้องรายงาน `status=valid` ไม่มีคำสั่งใดนำไฟล์มาใช้หรือเขียน receipt ที่ใช้งานอยู่ Bundle ประกอบด้วย `data/public/f2/`, `config/publication_contracts/f2_dashboard.json`, `serving-entries.json` และ `promotion-attestation.json` Promotion เปลี่ยน metadata ของสถานะการเผยแพร่ที่อนุมัติแล้ว ไม่ได้เปลี่ยนเนื้อหาสำคัญของ identity ราคา ที่ตั้ง หรือการตัดสินใจว่าจะเผยแพร่หรืองดเผยแพร่ฟิลด์ใด `deployment_approved=false` บันทึกขอบเขตของการอนุญาต ไม่ได้ปิดระบบ deployment

### 7. ตรวจการแทนที่ทั้งชุด แล้วนำมาใช้เมื่อได้รับอนุญาตเท่านั้น

**สำเนาสำหรับทดสอบการแทนที่** เป็นสำเนาชั่วคราวสำหรับทดลอง activation บนเครื่องก่อนใช้จริง เก็บไว้นอกพาธสาธารณะที่ใช้งานจริงและนอกข้อมูลนำเข้าของหลักฐาน/release/stage การตรวจ F2-only จากขั้นตอน 5 ใช้แทนกันไม่ได้

1. เลือก directory ใหม่ที่ยังไม่มีอยู่และตั้ง `OVERLAY` เป็น path นั้น คัดลอก `data/public/`, `config/publication_contracts/` และ `config/source_catalog.json` ปัจจุบันไปยัง relative path เดียวกันใต้ directory นั้น รวม serving manifest เดิมและ artifact ที่ไม่ใช่ F2 ด้วย เพราะ workspace ว่างไม่ได้ทดสอบการแทนที่จริง
2. **เฉพาะภายใน overlay เท่านั้น** ให้แทน `data/public/f2/` และ `config/publication_contracts/f2_dashboard.json` ด้วยไฟล์จาก bundle ที่ตรวจสอบแล้ว ใน `data/public/serving_manifest.json` ของ overlay ให้เก็บ entry ที่ไม่ใช่ F2 ทุกตัวไว้เหมือนเดิม และแทน entry ของ F2 ด้วย array `artifacts` จาก `serving-entries.json` ของ bundle ห้าม append สำเนา entry ของ F2 เก่าเพิ่มเป็นชุดที่สอง
3. สร้างและตรวจ receipt ของ overlay ด้วยตัวอย่างด้านล่าง ผลที่คาดคือ `status=valid` และไม่มีปัญหา ขั้นตอนนี้ตรวจ byte budget ของ workspace ทั้งชุด ความเป็นส่วนตัว ตัวตน hash และความเข้ากันได้ของรายการข้อมูลให้บริการ
4. เปรียบเทียบ hash ของไฟล์สาธารณะและ contract ที่ไม่ใช่ F2 ใน overlay กับ workspace ปัจจุบัน และเปรียบเทียบ serving entry ที่ไม่ใช่ F2 ในรูป structured data ทุกส่วนต้องไม่เปลี่ยน Receipt ต้องเปลี่ยนเมื่อ public revision เปลี่ยน ส่วน serving manifest เปลี่ยนเฉพาะ entry ของ F2
5. เก็บการตัดสินใจที่ผ่านการตรวจทาน ผลการตรวจสอบอิสระ ผล validation ของ overlay หลักฐานการรักษาข้อมูล และสำเนาสำรองของไฟล์ควบคุมก่อน activation ให้ผู้รับผิดชอบยืนยันการแทนที่บนเครื่องซึ่งได้รับอนุญาตแยกต่างหาก ก่อนนำไปใช้กับ workspace จริง

หลังเตรียม overlay แล้ว ให้รัน block นี้จาก root ของ repository คำสั่งจะเขียน receipt **ใต้ `$OVERLAY`** ไม่ใช่ใน active repository:

```bash
python - "$OVERLAY" <<'PY'
import json
import sys
from pathlib import Path
from app.publication import validate_workspace, write_receipt

root = Path(sys.argv[1]).resolve()
if root == Path.cwd().resolve():
    raise SystemExit("Use the prepared disposable overlay, not the active repository")
contracts = root / "config/publication_contracts"
catalog = root / "config/source_catalog.json"
write_receipt(root, contracts, catalog)
report = validate_workspace(root, contracts, catalog)
print(json.dumps(report, ensure_ascii=False, indent=2))
raise SystemExit(0 if report["status"] == "valid" else 1)
PY
```

หลัง activation ในเครื่องที่ได้รับอนุญาต ให้สร้างและตรวจ active receipt ใหม่ แล้วรัน repository gate:

```bash
python -m app.cli publication receipt
python -m app.cli publication validate
python -m app.cli check
```

ดูขอบเขต activation ที่ใช้ร่วมกันใน [ขั้นตอนการเผยแพร่](publication-workflow.md#f2-local-promotion) ห้ามแก้ artifact JSON ด้วยมือ อ้างว่าผ่านการยอมรับด้วยการเปลี่ยน status string, deploy หรือ push เพียงเพราะ candidate หรือ receipt ผ่าน validation

ผลลัพธ์ของ runbook นี้คือ public revision ที่ผ่านการตรวจทานและนำมาใช้ในเครื่องแล้ว ไม่ใช่เว็บไซต์ที่ deploy แล้ว ส่งการเปลี่ยนแปลงที่ตั้งใจไว้ผ่าน PR ทำตาม [CONTRIBUTING](../CONTRIBUTING.md) และตรวจผลกระทบของ deployment ก่อน merge หลัง deployment ทีมที่ได้รับอนุญาตจะตรวจ health และความครอบคลุมของฐานข้อมูล ระบบตรวจทานอัตโนมัติไม่ได้รัน production ingestion หรือเขียนแถวลงฐานข้อมูลโดยตรง

## ไฟล์ข้อมูลสาธารณะและฟิลด์ที่อนุญาต

### โครงสร้างไฟล์

ชุดข้อมูลสาธารณะประกอบด้วย `overview.json`, `geography.json`, ไฟล์ `topics/k*.json` จำนวน 14 ไฟล์, ไฟล์รายละเอียดแยกย่อย `details/*.json` ที่สร้างอย่าง deterministic และจำกัดขนาดไว้ รวมถึง `manifest.json` ไฟล์ย่อยทุกไฟล์ต้องอยู่ในรายการของทั้ง publication และ serving ส่วน manifest ใช้ระบุที่มาของชุดข้อมูล ไม่ใช่หัวข้อเพิ่มเติมใน UI

- **Overview:** นิยามของตัวชี้วัดหลักและตัวชี้วัดประกอบทั้งหมด ผลระดับประเทศ หน่วย สถานะ ข้อจำกัด source ID ความสามารถที่รองรับ และ artifact key
- **Geography:** รหัสจังหวัดมาตรฐานสองหลักครบ 77 จังหวัดและผลตามขอบเขตที่เลือก ข้อมูลภาคตามนิยามต้นทางที่รองรับ ความครอบคลุมของข้อมูลที่ไม่ทราบพื้นที่หรือมีพื้นที่ซ้อนกัน ข้อมูลประกอบที่แยกป้ายกำกับชัดเจน และเงื่อนไขการแสดงบนแผนที่ ห้ามแจกแจงค่าระดับอื่นลงจังหวัดโดยไม่มีหลักฐาน
- **Topic:** `filter_contracts`, `scopes` ที่คำนวณไว้แล้ว, `item_ids_by_measure_and_scope`, ดัชนีขนาดกระชับ `items_by_id`, `details_by_id`, `detail_lookup`, `detail_artifacts`, แหล่งข้อมูล และข้อจำกัด รายการและรายละเอียดต้องอ้างอิงดัชนีรายการที่อนุญาตให้แสดงสำหรับตัวชี้วัดที่เลือก
- **Result cell:** ค่า `value` ที่เป็นตัวเลขหรือ null จริง, `display_value`, หน่วย, `status` ที่บอกความหมายของข้อมูล, `availability` สำหรับคำขอนั้น, `scope_key`, ตัวกรองที่ขอและที่ใช้จริง รวมถึงเหตุผลเมื่อไม่มีข้อมูลให้แสดง ผู้ใช้ API ต้องไม่แปลงข้อความแสดงผลกลับเป็นตัวเลข หรือคำนวณค่าใหม่จากความยาวของรายการ

ส่วนที่นับเอนทิตีต้องตรวจสอบให้จำนวนที่นับทั้งหมด จำนวนที่อนุญาตให้แสดงรายละเอียด และจำนวนที่งดแสดงรายละเอียดทั้งรายการสอดคล้องกัน ส่วนข้อมูลรวมแสดงองค์ประกอบและหน่วยของข้อมูลตามที่ประกาศไว้ ไม่สร้างรายชื่อบุคคลหรือธุรกิจขึ้นเอง รายละเอียดหนึ่งรายการอาจใช้ร่วมกันได้หลายตัวชี้วัดหรือหลายขอบเขต แต่ยังต้องตรวจว่าอยู่ในขอบเขตที่ขอจริง

### รายละเอียดที่เผยแพร่ได้

การสร้าง public projection ต้องเลือกฟิลด์ที่ระบุไว้เท่านั้น ห้าม serialize แถวภายในหรือข้อมูลในช่อง `*_details_json` ทั้งก้อนโดยไม่คัดเลือก ต้องใช้นโยบายเฉพาะของแต่ละแหล่งข้อมูล, [field contexts](field-contexts.md) ที่อนุมัติในระดับฟิลด์ปลายทาง, การกรองข้อความ, การตรวจที่มา, ข้อจำกัดขนาดไฟล์ และลำดับข้อมูลที่แน่นอน

| กลุ่มรายละเอียด | ฟิลด์ที่อนุมัติและข้อจำกัด |
|---|---|
| พื้นที่วัฒนธรรม K01B และรายการที่ผูกกับพื้นที่ใน K12 | ชื่อหรือข้อความแสดงผล คำอธิบาย/ประวัติบางส่วนที่ปลอดภัย หมวดหมู่ ความไม่แน่นอนของ identity ความเชื่อมโยงกับแหล่งข้อมูล ที่ตั้งตามเขตการปกครองที่มีหลักฐาน แหล่งอ้างอิงที่อนุญาต และลิงก์สื่อที่ผ่านการคัดเลือก K12 รวมบุคคลและผู้ถือครององค์ความรู้ด้วย ไม่ได้มีเฉพาะสถานที่ที่ไม่ใช่บุคคล |
| ผู้ประกอบการ K05 | ชื่อหรือข้อความแสดงผล identity/ความไม่แน่นอน ความเชื่อมโยงกับกลุ่มหรือพื้นที่ หลักฐานทางธุรกิจที่ปลอดภัย พื้นที่ตามเขตการปกครองของผู้ประกอบการเอง และความสัมพันธ์กับสินค้า/บริการที่มีหลักฐาน ไม่เผยแพร่รายชื่อผู้ประกอบการระดับบุคคล ข้อมูลติดต่อส่วนตัว ราคา หรือรูปภาพ |
| ธุรกิจที่เข้าร่วมใน C08 | ชื่อจาก Learning Area Based หรือป้าย `Name unavailable` ที่ระบุชัดเจน, identity ชั่วคราว, พื้นที่ของธุรกิจเอง และบริบทการเข้าร่วม/โครงการ/หน่วยวิจัย/ปีงบประมาณ ไม่ถือเป็นหลักฐานว่าธุรกิจพัฒนาขึ้น ไม่เชื่อมกับผลประเมินรายบุคคล ไม่เผยแพร่ประวัติแบบบรรยาย ราคา หรือสื่อ |
| กลุ่มสินค้า/บริการ K07 (offering family) | ชื่อกลุ่ม หมวดหมู่ สถานะ รายการสินค้า/บริการและรุ่นย่อยที่เก็บไว้ คำอธิบายที่คัดเลือก พื้นที่ของสินค้า/บริการนั้นเอง ความสัมพันธ์และแหล่งอ้างอิงที่มีหลักฐาน ราคาของแต่ละสมาชิกที่ระบุเจ้าของราคาแยกกัน และลิงก์สื่อที่ผ่านการคัดเลือก |
| กิจกรรม K03 | ชื่อหรือข้อความแสดงผล คำอธิบายที่คัดเลือก วันที่ที่ระบุจริง สถานที่จัดกิจกรรม ช่วงกิจกรรมย่อย ลิงก์เผยแพร่ผลงาน และเครดิตที่มีหลักฐาน รายการที่อนุญาตแตกต่างกันตามแหล่งข้อมูล ช่วงกิจกรรมย่อยและรายการเผยแพร่ผลงานไม่เพิ่มจำนวนครั้งของกิจกรรมที่นับ |
| นวัตกรรม K04 และ C04_LISTED | ชื่อ คำอธิบายที่คัดเลือก ระเบียนต้นทาง assertion เรื่องระดับความพร้อม พื้นที่การใช้ประโยชน์ที่มีหลักฐาน และเครดิตผลงาน/หน่วยงานที่มีความเชื่อมโยงระบุไว้ชัดเจน ระดับความพร้อมไม่ใช่คะแนนพัฒนาการของบุคคล ไม่คัดเลือกราคาหรือสื่อมาเผยแพร่ |
| บุคคล C02 | เครดิตผลงานสาธารณะในขอบเขตจำกัด assertion ที่ทำให้ผ่านเกณฑ์ และข้อมูลพื้นที่เฉพาะระดับจังหวัดที่ผ่านการตรวจทาน ตามข้อกำหนดแยกด้านล่าง |

การอนุมัติครั้งแรกครอบคลุมรายละเอียดของตัวชี้วัดหกรายการ จากนั้นมีการอนุมัติ K01B/K12 เพิ่มแยกต่างหาก และมีการอนุมัติฟิลด์บุคคล พื้นที่ และแผนที่ข้อมูลรวมของ C02 ตามมา การตัดสินใจแต่ละครั้งมีขอบเขตเฉพาะ ไม่ใช่สิทธิ์เผยแพร่ทุกฟิลด์จากต้นทาง

กติกาที่ใช้ร่วมกัน:

- เผยแพร่ความสัมพันธ์ที่มีหลักฐานจริง ไม่อนุมานชื่อหรือหน่วยงานจากข้อความบรรยาย แม้ adapter จะใช้อินเทอร์เฟซร่วมกัน แต่รายการที่อนุญาตของแต่ละแหล่งยังต่างกัน
- เก็บให้ชัดว่าที่ตั้งเป็นของใครและใช้ในบทบาทใด รายละเอียดทั่วไปที่อนุมัติและไม่ใช่ C02 อาจมีรหัส/ชื่อจังหวัด อำเภอ และตำบลเมื่อมีหลักฐาน ระดับที่ไม่มีหลักฐานต้องคงเป็นไม่ทราบ ไม่เผยแพร่ที่อยู่ระดับถนนหรือพิกัดละเอียด ส่วน C02 เข้มงวดกว่า โดยอนุญาตเฉพาะจังหวัด
- ไม่เผยแพร่ credentials, cookies, รหัสบัญชี/โปรไฟล์, tokens, ลิงก์ยืนยันตัวตน/รีเซ็ตบัญชี, HTML หรือ payload ดิบ, พาธหรือตัวชี้ตำแหน่งหลักฐานส่วนตัว, ข้อมูลติดต่อส่วนตัว และข้อมูลสุขภาพ/ครัวเรือน/การเงิน/ผลประเมินระดับบุคคล การลบชื่อออกไม่ได้ทำให้ผลประเมินรายบุคคลเผยแพร่ได้
- หากฟิลด์หนึ่งไม่ปลอดภัย ให้งดเผยแพร่เฉพาะฟิลด์นั้นก่อนพิจารณาตัดรายละเอียดที่เหลือซึ่งปลอดภัยทั้งรายการ และเก็บเหตุผลที่ละฟิลด์หรือรายการย่อยไว้ ข้อยกเว้นสำหรับชื่อรายการไม่ครอบคลุมฟิลด์อื่นที่ไม่เกี่ยวข้อง
- URL สาธารณะต้องตรงกับกฎ source/host/path ที่อนุมัติ และคงการระบุแหล่งที่มาไว้ หากใช้ลิงก์หน้า portal แทนหน้ารายการ ต้องติดป้าย `link_scope=source` ไม่ใช่แสร้งว่าเป็นลิงก์เฉพาะรายการ เส้นทาง API รายระเบียนของ RINMP ที่ไม่ได้ลงทะเบียนยังไม่เผยแพร่ รายการฐานเดิม 630 รายการใช้การอ้างอิงหน้า portal ของต้นทางและรหัสรายการที่ไม่เปิดเผยความหมายแทน

### ราคา สื่อ และข้อยกเว้น

ราคา K07 เป็นค่าที่ต้นทางรายงานสำหรับสมาชิกแต่ละรายการ โดยต้องไม่ติดลบ และมาจาก observation ของ AtLocal, CulturalMap และ iCommunity ที่อยู่ในรายการอนุญาต เก็บสกุลเงิน สถานะการแปลงราคา และบริบทของ snapshot ไว้ ห้ามยุบราคาของสมาชิกที่ต่างกันให้เหลือราคาเดียวของทั้งกลุ่ม ค่า 0 ต้องแสดงเป็น **`price unspecified/source reports 0`** เท่านั้น ไม่ใช่ “ฟรี” หน่วยขายและวันที่ราคามีผลที่ต้นทางไม่ได้ระบุต้องคงเป็น `not_reported` จำนวนทศนิยมของสกุลเงินหรือคำขยายในข้อความอิสระไม่ใช่หลักฐานให้อนุมานหน่วยขาย สถานะ active/มีสินค้าในต้นทางไม่ได้ยืนยันว่าสินค้ายังพร้อมขายในปัจจุบัน

สื่อเผยแพร่ได้ในรูป **ข้อมูลอ้างอิงเท่านั้น** ได้แก่ ลิงก์ HTTPS ที่ผ่านเงื่อนไขของแหล่งข้อมูล เครดิตที่มา และสถานะ `source_reference_not_fetched`/อ้างอิงเท่านั้น ไม่อนุญาตให้โหลดอัตโนมัติ แสดง preview, prefetch, proxy, คัดลอก หรือให้บริการไฟล์แทนต้นทาง prefix `/file-upload/` และ `/gallery/` ที่อนุญาตเพิ่มสำหรับ CulturalMap ใช้เฉพาะ URL สื่อที่ผ่านเกณฑ์ ไม่ได้ขยายสิทธิ์ของลิงก์ต้นทางทั่วไปหรือ source catalog ที่สร้างไว้

ต้องคงข้อยกเว้นที่ผ่านการตรวจทานแล้วดังนี้:

- identity ของ K12 จำนวน 26 รายการที่อาจซ้ำกันยังต้องแยกไว้และแสดงความไม่แน่นอน ไม่ต้องเพิ่มด่านตรวจว่าเป็นสิ่งที่ไม่ใช่บุคคลหรือแก้รายการซ้ำใหม่ เพียงเพื่อแสดงรายละเอียดส่วนที่ปลอดภัยซึ่งอนุมัติแล้ว
- ข้อยกเว้นชื่อมรดกวัฒนธรรมทั้งสิบกรณีผูกกับค่าที่ระบุไว้โดยเฉพาะ ไม่ใช่ข้อยกเว้นให้เผยแพร่ที่อยู่ทั่วไป เครื่องหมาย ampersand ต้องคงเป็นข้อความ
- CD-5342 ต้องคงรายละเอียดส่วนที่ปลอดภัยและระบุชัดว่างดแสดงชื่อ คำอธิบายจากต้นทางไม่ใช่สิทธิ์ให้แต่งชื่อทดแทน
- CD-2073 และ CD-1642 ต้องไม่ทำให้ผู้อ่านเข้าใจว่าบ้านส่วนตัวหรือบ้านที่ปิดอยู่เปิดให้บุคคลทั่วไปเข้าชม การอนุญาตให้แสดงชื่อไม่ได้อนุญาตให้เผยแพร่ที่อยู่ พิกัด หรือข้อความบรรยายทั้งหมด
- กรณีชื่อของนวัตกรรมที่ถูกตรวจผิดว่าเป็นข้อมูลติดต่อบนสื่อสังคม ผูกข้อยกเว้นไว้กับเอนทิตี source key และ hash ของชื่อดิบที่ระบุเท่านั้น ไม่ใช่สิทธิ์เผยแพร่ข้อมูลติดต่อทั่วไป
- หน่วยธุรกิจ C08 สี่รายการที่ชื่อผิดรูปแบบยังคง identity ชั่วคราวแยกกัน และแสดงข้อมูลการเข้าร่วม/ที่ตั้งส่วนที่ปลอดภัย พร้อมป้าย `Name unavailable` ที่ระบุว่าเป็นข้อความที่ระบบสร้าง
- หลักฐานสุขภาพส่วนบุคคลของ CD-3768 ต้องถูกตัดออกในระดับฟิลด์ แต่ identity และหลักฐานธุรกิจส่วนที่ปลอดภัยยังคงอยู่ ห้ามคัดลอกข้อความอ่อนไหวนั้นมาไว้ในเอกสาร

### ข้อจำกัดขนาดข้อมูล

เพดานขนาดข้อมูลสาธารณะทั้ง workspace ที่ผู้มีอำนาจอนุมัติไว้คือ **160 MiB** ไม่ใช่งบขนาดสำหรับ F2 เพียงส่วนเดียว เพดานต่อไฟล์เริ่มต้นของระบบกลางยังเป็น 25 MiB ส่วนเป้าหมายขนาดไฟล์ topic และไฟล์รายละเอียดแยกย่อยของ F2 ที่ผ่านการตรวจทานคือ 8 MiB และ 4 MiB ตามลำดับ ต้องบังคับใช้ค่าจริงจาก policy/contract ที่เลือกสำหรับแต่ละ output การแบ่งไฟล์ช่วยให้อ่านเฉพาะส่วนได้ แต่ไม่ได้ทำให้ขนาดรวมลดลง

วัดขนาดสำเนาทดสอบการแทนที่ทั้งชุด รวมทั้งไฟล์ที่ไม่ใช่ F2 และไฟล์ควบคุมด้วย ห้ามเพิ่มเพดาน ตัดบุคคลที่ถูกนับ ทอนเนื้อหาที่อนุมัติ หรือตัดตัวชี้วัดเพื่อให้ขนาดพอดี การเปลี่ยนเพดานต้องได้รับอนุมัติแยกจากการอนุมัติฟิลด์หรือ local promotion ขนาดรวมที่บันทึกไว้ในอดีตไม่ใช่ผลวัดความจุของชุดปัจจุบัน

## ข้อกำหนดข้อมูลบุคคล C02

### สมาชิกและ identity

`C02_COMMUNITY` เป็นกลุ่มประชากรประกอบภายใต้ K02 ไม่ใช่รายชื่อบุคคลที่อยู่เบื้องหลัง K02 ไม่ใช่ชุดที่ใช้ทำให้ยอด K02 ตรงกัน และไม่ใช่ส่วนที่นำไปบวกกับ K02 ผู้ผ่านเกณฑ์ต้องมี assertion ที่ยอมรับแล้วว่าเป็น `community_innovator` (นวัตกรชุมชน) หรือ `inventor` (ผู้ประดิษฐ์) บทบาทนักวิจัย เจ้าของ ผู้ถือสิทธิ์ และสมาชิกหน่วยงานเพียงอย่างเดียวไม่ทำให้ผ่านเกณฑ์ บริบทนักวิจัยจาก `f2_target_household` ไม่ได้เปลี่ยนกติกานี้

public projection ใช้ `global_person_id` และ assertion ที่ทำให้ผ่านเกณฑ์ซึ่งได้รับการยอมรับแล้ว ไม่ทำ identity/eligibility resolution ใหม่ และไม่อนุมานบทบาทจากชื่อที่แสดง ID ต้องไม่ใช่รหัสบัญชี token ข้อมูลติดต่อ หรือลำดับแถว สถานะ global identity ยังคงเป็น `source_supported` และ `reviewed_cross_source` ส่วนความไม่แน่นอนระดับแหล่งข้อมูลและ quality flag แยกจากกัน บุคคลที่อาจซ้ำกันแต่ยังตัดสินไม่ได้ต้องคงแยกไว้

การเป็นสมาชิกที่ถูกนับกับการได้รับอนุญาตให้แสดงรายละเอียดสาธารณะเป็นคนละเรื่อง:

```text
counted_total = public_detail_total + withheld_count
```

ID ที่ถูกนับแต่ไม่แสดงรายละเอียดต้องมีเหตุผลงดแสดงทั้งรายการที่ผ่านการตรวจทานหนึ่งเหตุผล public item ID ต้องเป็นส่วนหนึ่งของประชากรที่ยอมรับแล้ว และมีรายละเอียดหนึ่งรายการต่อ global person ที่อนุญาตให้แสดง ให้ลองงดเผยแพร่เฉพาะฟิลด์ที่ไม่ปลอดภัยก่อน หากต้องงดแสดงชื่อ ยังอาจเก็บรายละเอียดส่วนที่มีประโยชน์และปลอดภัยไว้ภายใต้ป้าย `ชื่ออยู่ระหว่างการตรวจสอบ` ได้ แต่ป้ายนี้ไม่ได้ให้สิทธิ์เผยแพร่บทบาท หน่วยงาน ความสัมพันธ์ หรือฟิลด์จากต้นทางใดเพิ่มขึ้นเอง

### ดัชนีขนาดกระชับและรายละเอียดบุคคล

ใช้ `f2/topic/k02` และ shard ที่ประกาศไว้ในรูป `f2/topic/k02/detail/NNN` ดัชนี `items_by_id` ประกอบด้วย `label`, `label_availability`, `identity_status`, `source_ids`, `role_codes`, `role_labels_th`, ฟิลด์ทางเลือก `organization_labels` และ `related_work_count` ห้ามคัดลอกรายละเอียดเต็ม ประวัติบุคคล หรือข้อมูลติดต่อมาใส่ซ้ำในดัชนีรายการ

โครงสร้างรายละเอียดเก็บ `entity_id`, ชื่อ/สถานะการแสดงชื่อ, สถานะ identity, แหล่งข้อมูล/ระบบต้นกำเนิดที่อนุญาต, รายการจากต้นทาง, ความสัมพันธ์, ที่ตั้ง, รหัสจังหวัด และ flags ส่วน `children.qualifying_roles` อธิบายว่าเหตุใดบุคคลจึงผ่านเกณฑ์ โดยมี assertion ID ที่ยอมรับแล้ว บทบาทที่ปรับเป็นมาตรฐาน/ข้อความแสดงผล `qualifies_for` หลักฐานที่รองรับ และแหล่งข้อมูลที่อนุญาต ใส่บริบทหน่วยงานหรือผลงานที่เกี่ยวข้องได้เฉพาะเมื่อมีหลักฐานรองรับส่วนนั้นแยกต่างหาก `children.organizations` ต้องมีความสัมพันธ์ระหว่างบุคคลกับหน่วยงานอย่างชัดเจน ไม่ใช่นำหน่วยงานของนวัตกรรม เจ้าของโครงการ หรือหน่วยงานที่ปรากฏในหน้าเดียวกันมาใช้แทน

ชื่อบุคคลต้องมีต้นทางสาธารณะที่ชัดเจนและอยู่ใน field context สำหรับเครดิตผลงานที่อนุมัติแล้ว ห้ามอนุมานชื่อจากข้อความบรรยายหรือใช้รหัสโปรไฟล์/ข้อมูลติดต่อแทน C02 ไม่เผยแพร่อีเมล โทรศัพท์ ที่อยู่ระดับถนน พิกัด รหัสบัญชีสื่อสังคมส่วนตัว ประวัติบุคคลที่ไม่ได้ตรวจทานโดยตรง รหัสบัญชี/โปรไฟล์ ผลประเมิน หรือข้อมูลส่วนบุคคลอ่อนไหว แม้ข้อมูลในโดเมนอื่นอาจอนุญาตข้อมูลติดต่องานบางส่วนในขอบเขตเฉพาะก็ตาม

ความสัมพันธ์จะมี `target_detail` ได้ก็ต่อเมื่อปลายทางได้รับอนุญาตให้แสดงใน public revision เดียวกัน และระบุ topic, measure และ entity ID ที่ตรงกัน หากไม่เข้าเงื่อนไข ให้เก็บเฉพาะเครดิตที่ปลอดภัยและมีหลักฐานแยกต่างหากเป็นข้อความ โดยไม่เดาลิงก์ `related_work_count` นับผลงานสาธารณะที่อนุญาตและมี identity ไม่ซ้ำกัน ไม่ได้นับ assertion ซ้ำหรือผลงานตลอดชีวิต หากยังพิสูจน์ identity ที่แตกต่างกันของผลงานที่อนุญาตไม่ได้ ห้ามสร้าง identity หรือจำนวนขึ้นเอง การนำทางปัจจุบันเชื่อมทางเดียวจาก C02 ไปยังรายละเอียด K04/C04 ที่อนุญาต การแสดงรายชื่อบุคคลย้อนกลับจากผลงานยังอยู่นอกขอบเขตนี้

topic ต้องเก็บ `item_ids_by_measure_and_scope`, `detail_lookup` และ `detail_artifacts` ไว้ ใช้ mapping ที่ประกาศไว้ ไม่สร้างชื่อไฟล์ shard จากข้อมูลใน request เอง ID ที่อนุญาตแต่ละตัวต้องชี้ไปยังรายละเอียดเพียงหนึ่งรายการ ทุก shard ต้องอยู่ในรายการและผ่านการตรวจ hash การขอรายการไม่โหลด shard รายละเอียดบุคคล ส่วนการขอรายละเอียดโหลดเฉพาะไฟล์ย่อยที่ประกาศไว้และจำเป็นต่อคำขอนั้น

### จังหวัดและแผนที่ข้อมูลรวม

C02 รองรับเฉพาะขอบเขตระดับประเทศ และตัวกรอง **จังหวัดที่ต้นทางระบุสำหรับนวัตกร** ที่ผ่านการตรวจทาน โดยเลือกได้ครั้งละหนึ่งจังหวัด ป้ายใน UI คือ **จังหวัดที่ต้นทางระบุสำหรับนวัตกร** และใช้ location role `source_reported_innovator_location` ข้อมูลนี้ไม่ได้หมายถึงที่อยู่อาศัยหรือสถานที่ทำงานปัจจุบัน

การอนุญาตข้อมูลพื้นที่ต้องเชื่อม source-local iCommunity innovator ID ที่ตรงกันกับ global identity ที่ผ่านการตรวจทาน ห้ามเชื่อมด้วยชื่อ อาจอนุญาตข้อมูลจังหวัดที่ชื่อตรงกับชื่อมาตรฐานทุกตัวอักษรได้ แม้ยังแก้ลำดับชั้นอำเภอ/ตำบลไม่สำเร็จ แต่กรณีรหัสพื้นที่จากต้นทางขัดแย้งกันยังต้องตัดออก เผยแพร่ได้เฉพาะรหัส/ชื่อจังหวัดและบริบทต้นทางที่อนุญาต ข้อมูลเขตการปกครองระดับต่ำกว่า รหัสพื้นที่ พิกัด source location ID, observation ID และตัวชี้ตำแหน่งหลักฐานส่วนตัวต้องอยู่ภายใน ห้ามยืมพื้นที่จากผลงาน หน่วยงาน โครงการ หน่วยวิจัย บุคคลอื่น หรือ metadata ของหน้าแหล่งข้อมูล

ชุดข้อมูลฐานที่ใช้อยู่มีบุคคล 4,640 คน: 4,415 คนมีความเชื่อมโยงกับจังหวัดรวม 4,418 รายการใน 37 จังหวัด, 225 คนยังอยู่เฉพาะระดับประเทศ และสามคนมีความเชื่อมโยงกับจังหวัดซ้อนกัน กรณีรหัสพื้นที่ต้นทางขัดแย้งกันสิบแปดกรณียังไม่ถูกนำมาใช้ ในแต่ละจังหวัดให้นับบุคคลไม่ซ้ำ ไม่ใช่จำนวนความเชื่อมโยงหรือ assertion จากต้นทาง

การอนุมัติ `map_availability=province` อนุญาต **แผนที่ระบายสีรายจังหวัด (choropleth) ของข้อมูลรวมในขอบเขตมาตรฐาน 77 จังหวัด** ไม่ใช่แผนที่จุดบุคคล ต้องแยก 40 จังหวัดที่ไม่มีสมาชิกออกจากกรณีไม่มีข้อมูลให้แสดง และใช้คำอธิบายสีของข้อมูลรวมที่ผ่านการตรวจทาน ไม่อนุญาตตัวกรองภาค ปี บทบาท หรือหน่วยงาน ไม่อนุญาตตำแหน่งละเอียดหรือการอนุมานที่อยู่อาศัย/สถานที่ทำงาน การอนุมัติแผนที่ข้อมูลรวมนี้ใช้แทนสถานะเดิมที่อนุญาตเพียงตัวกรองจังหวัด แต่ไม่ได้ยกเลิกข้อจำกัดของข้อมูลที่ตั้งบุคคล

## API และ Dashboard

ชั้น serving อ่านเฉพาะ public artifact ที่ผ่านการตรวจทาน ผ่าน `PublicArtifact` หรือ public-file fallback ที่อนุมัติ ไม่ดึงข้อมูลจากต้นทาง ไม่อ่าน private release ไม่ทำ ingestion ใหม่ ไม่ resolve identity และไม่คำนวณ KPI ใหม่ระหว่าง startup, health check หรือการตอบ request API เลือกค่าที่คำนวณไว้ล่วงหน้าและดัชนีที่อนุญาต ส่วน frontend จัดรูปแบบเพื่อแสดงผล

| Route ภายใต้ `/api/public/v1/f2` | การทำงาน |
|---|---|
| `GET /overview` | คืนชุดผลระดับประเทศหรือ `province=<code>` พร้อมระบุชัดเมื่อขอบเขตที่ขอไม่รองรับ |
| `GET /map?measure=<id>` | คืนค่าขนาดกระชับและคำอธิบายสีที่ผ่านการตรวจทานสำหรับตัวชี้วัดหนึ่งรายการที่รองรับจังหวัด ใช้ได้เฉพาะตัวกรองที่ไม่ใช่พื้นที่ซึ่งประกาศว่ารองรับ |
| `GET /topics/{topic_id}` | คืนตัวชี้วัด/ขอบเขตที่เลือก ตัวเลือกที่ใช้ได้ ที่มา และหน้ารายการที่อนุญาตเมื่อรองรับ โดย `measure` เริ่มต้นเป็นตัวชี้วัดหลักของ topic |
| `GET /topics/{topic_id}/details/{entity_id}?measure=<id>` | คืนรายละเอียดหนึ่งรายการที่อยู่ในตัวชี้วัดและขอบเขตที่ขอ โดยค้นจากรายละเอียดในไฟล์หลักหรือไฟล์ย่อยตาม lookup ที่ประกาศไว้ |

พารามิเตอร์ query ที่ใช้ได้เมื่อ route และตัวชี้วัดนั้นรองรับ ได้แก่ `province`, `category`, `source_level`, `source_region`, `component`, `source_dimension`, `q`, `limit`, `offset`, `revision` route รายละเอียดใช้พารามิเตอร์ของตัวชี้วัด/ขอบเขตที่ประกาศไว้ ไม่ใช้ pagination พารามิเตอร์ที่ไม่รู้จักหรือชุดตัวกรองที่ไม่รองรับถือเป็นข้อผิดพลาด ไม่มีพารามิเตอร์ให้ผู้เรียกกำหนดพาธ artifact ตามอำเภอใจ

- รายการมีค่าเริ่มต้น 25 รายการ สูงสุด 100 รายการ และ offset ต้องไม่ติดลบ ค้นหาได้เฉพาะชื่อหรือข้อความแสดงผลที่อนุญาต ความยาวคำค้นไม่เกิน 200 ตัวอักษร ไม่ค้นประวัติบุคคล หน่วยงาน หรือข้อมูลดิบ ลำดับผลต้องแน่นอน
- แยกค่า KPI ใน `result`, จำนวนรายการในขอบเขต, จำนวนที่ตรงกับคำค้น และจำนวนรายการในหน้านั้นออกจากกัน topic ที่เป็นข้อมูลรวมอย่างเดียวไม่ได้รับความสามารถค้นหาหรือแสดงรายชื่อเพิ่มขึ้นเอง
- response ผูกกับ revision ที่เป็น hash ของ manifest ปัจจุบัน ผู้เรียกส่ง `revision` เพื่อป้องกันการนำทางข้ามรุ่นข้อมูลได้ เอนทิตีที่ไม่รู้จักหรือไม่อยู่ในขอบเขตคืน 404; ตัวกรอง/pagination ไม่ถูกต้องคืน 422; revision ที่ขอล้าสมัยคืน 409; ข้อมูล publication ที่จำเป็นขาดหายหรือไม่สอดคล้องกันคืน 503 ไม่ใช่ response สำเร็จที่ว่างเปล่า
- ETag เปลี่ยนตาม revision และ request ที่ปรับเป็นรูปแบบมาตรฐาน URL ของ revision ปัจจุบันใช้การตรวจสอบความสดใหม่ซ้ำ (`public, max-age=0, must-revalidate`) และรองรับ 304 ห้ามเรียก URL เหล่านี้ว่า immutable
- การอ่าน artifact ของ F2 ขณะตอบ request เลือกเฉพาะส่วนและมี cache ตาม revision/hash พร้อมขอบเขตขนาดชัดเจน: request ภาพรวมหรือรายการไม่โหลดไฟล์รายละเอียดทุกไฟล์ ส่วน startup ของแอปเป็นอีกขั้นตอนหนึ่งที่ตรวจสอบและ sync artifact ตาม serving inventory รวมถึงไฟล์รายละเอียดเข้าฐานข้อมูล serving-policy cache ของระบบกลางช่วยเลี่ยงการสแกนข้อมูลซ้ำเมื่อทั้ง bytes และ policy ไม่เปลี่ยน แต่ต้องตรวจใหม่เมื่อเนื้อหาหรือนโยบายเปลี่ยน candidate adapter สำหรับทดสอบจะตรวจ hash ของ candidate และแทนที่ I/O เฉพาะใน tests เท่านั้น production ต้องไม่ import adapter นี้

Dashboard ใช้โครงหน้าร่วมเดิมและมีสามแท็บ: **ภาพรวม**, **รายการ**, **ที่มาและข้อจำกัด** แสดงตัวชี้วัดหลัก 14 รายการและตัวชี้วัดประกอบเจ็ดรายการ รองรับการนำทางระดับประเทศ/จังหวัดโดยไม่ผ่านขั้นภาคของ Dashboard ใช้ตัวเลือกที่เหมาะกับแต่ละตัวชี้วัด และใช้ตารางภาคตามนิยามต้นทางในกรณีที่ไม่รองรับการแสดงรายจังหวัด

โหลด F2 เมื่อจำเป็น (lazy loading) และยกเลิกหรือไม่นำผลจาก request เก่ามาแสดง เก็บตัวชี้วัด ขอบเขต ตัวกรอง คำค้น/หน้า และรายละเอียดที่เลือกไว้ใน URL เพื่อให้เปิดกลับมาได้ เมื่อเปลี่ยนตัวชี้วัดหรือขอบเขตต้องล้างตัวเลือกที่ใช้ร่วมกันไม่ได้ การปิดรายละเอียดหรือกด Back ในเบราว์เซอร์ต้องกลับไปยังรายการและคืน keyboard focus ให้รายการที่ใช้เปิดรายละเอียด ใช้แผงรายละเอียดบน desktop หรือหน้าต่างรายละเอียดแบบ sheet บนมือถือที่รองรับการเข้าถึง (accessibility) แสดงสถานะกำลังโหลด/ผิดพลาด/ลองใหม่ให้ชัดเจน render ข้อความอย่างปลอดภัย และไม่ร้องขอสื่ออัตโนมัติ

ส่วนแสดงผล C02 ต้องแสดงบทบาทที่ทำให้ผ่านเกณฑ์ทั้งสองประเภท หน่วยงาน ความไม่แน่นอน ลิงก์ผลงานที่ปลอดภัย และคำอธิบายว่าไม่ได้ใช้ทำยอดให้ตรงกับ K02 ในมุมมองหลัก ส่วน technical ID และสถานะดิบต้องอยู่ในหัวข้อทางเทคนิคที่ยุบไว้ ข้อความแทนชื่อที่ระบบสร้างต้องไม่ดูเหมือนชื่อจากต้นทาง

เป้าหมายขนาด payload ของภาพรวม/แผนที่แรกเข้าและหน้ารายการ 25 รายการคือไม่เกิน 256 KiB ก่อนบีบอัด โดยไม่นับ geometry ของแผนที่และ assets ที่ใช้ร่วมกัน เมื่อแก้เส้นทางนี้ให้วัดการอ่านแบบ cold/warm จำนวนการเข้าถึง artifact และขนาด response อย่าอ้างผลวัดเก่าเป็นการรับประกันปัจจุบัน หรือลดข้อมูลที่อนุมัติแล้วเพื่อให้ถึงเป้าหมาย

ตัวอย่างลำดับการเรียก API:

1. เรียก `/api/public/v1/f2/topics/k04?measure=K04&limit=25` เพื่อดู topic K04 ระดับประเทศ
2. แสดง `result` ที่ผ่านการตรวจทานแยกจาก `list` ที่แบ่งหน้า การค้นหาอาจลดจำนวนรายการที่ตรงคำค้น โดยไม่เปลี่ยน KPI
3. เลือกเอนทิตีที่อนุญาตจากรายการนั้น แล้วเรียก `/api/public/v1/f2/topics/k04/details/{entity_id}?measure=K04&revision={revision}` โดยแทน placeholder ทั้งสองด้วยค่าจาก topic response หากเลือกจังหวัดหรือตัวกรองอื่นที่รองรับไว้ ให้ส่งขอบเขตเดียวกันในคำขอรายละเอียดด้วย
4. หากได้ 409 ให้โหลด topic/revision ปัจจุบันก่อนลองใหม่ ส่วน 503 หมายถึงข้อมูลที่ผ่านการตรวจทานขาดหายหรือไม่สอดคล้องกัน ไม่ใช่รายการว่าง

ใช้ entity ID และข้อมูล lookup ที่ response ระบุ client เรียกผ่าน detail endpoint ไม่สร้างชื่อไฟล์ shard หรือเข้าถึงพาธหลักฐานส่วนตัวเอง

## การตรวจสอบและแก้ปัญหา

ใช้ environment ของโครงการที่ activate แล้วตามหัวข้อ [เริ่มต้นใช้งาน](#เริ่มต้นใช้งาน) พร้อม dependencies จาก `requirements.txt` ชุดทดสอบต้องไม่พึ่งหลักฐานหรือไฟล์อนุมัติส่วนตัวของนักพัฒนาคนใด

environment บนเครื่องในอดีตเคยต้องใช้ `python_fallback`, `PYTHONPATH` ที่ตั้งเอง หรือ `DISABLE_SQLALCHEMY_CEXT_RUNTIME` สิ่งเหล่านี้เป็นวิธีแก้ชั่วคราวในอดีต ไม่ใช่ขั้นตอนติดตั้ง หากเกิดข้อผิดพลาดจาก native extension อีก ให้หาสาเหตุของ environment แทนการเพิ่มทางเลี่ยง Automated agent ต้องปฏิบัติตามกติกาการขออนุญาตของ repository ก่อนติดตั้ง dependencies

ชุดตรวจเฉพาะสำหรับการแก้ pipeline:

```bash
python -m pytest -q tests/f2_pipeline
```

เลือก tests เพิ่มตามสิ่งที่เปลี่ยน:

| สิ่งที่เปลี่ยน | ชุดตรวจที่เกี่ยวข้อง |
|---|---|
| ระบบ publication/privacy กลาง หรือ serving-policy cache | `tests/test_publication.py`, `tests/test_field_contexts.py`, `tests/test_public_artifacts.py` |
| พฤติกรรม API/ตัวกรอง/revision ของ F2 | `tests/test_f2_api.py`, `tests/test_f2_c02_api_contract.py` |
| การแสดงผล/การนำทางของ F2 | `tests/test_f2_detail_presentation.py`, `tests/test_ui_coverage.py` และตรวจผ่านเบราว์เซอร์บนเครื่อง |
| การทำงานร่วมกับ private candidate จริง | `tests/test_f2_c02_candidate_integration.py` เมื่อมี candidate ตามที่กำหนดไว้ หากไม่มีอาจเกิด skip ที่คาดหมายได้ |

หลักฐานที่ใช้เฉพาะกับ candidate ยังคงเป็นข้อมูลส่วนตัว และต้องไม่กลายเป็น dependency ของ production หรือ CI ทั่วไป ตัวอย่างเช่น รัน `python -m pytest -q tests/test_f2_api.py` สำหรับ API tests หรือเลือกไฟล์อื่นจากตารางตามสิ่งที่เปลี่ยน เมื่อรวมการเปลี่ยนแปลงด้านพฤติกรรมแล้ว ให้รันชุดตรวจเต็มด้านล่าง

ก่อนเปิด PR และหลังรวมการเปลี่ยนแปลงด้านพฤติกรรม/publication ให้รันชุดตรวจที่กำหนด:

```bash
python -m app.cli check
```

คำสั่งนี้รัน compile, pipeline validation, publication validation, การตรวจขอบเขต public repository และ pytest ตัวเลือก `--skip-tests` ใช้ตรวจระหว่างทางแบบเร็ว ไม่ใช่เกณฑ์ผ่านขั้นสุดท้าย ควรรันชุดเต็มหลังรวมงานแล้ว แทนการรันซ้ำทุกครั้งที่แก้จุดเล็ก ๆ หากเปลี่ยนเฉพาะเอกสาร สามารถตรวจลิงก์ ความถูกต้องของ CLI และยืนยันว่า hash ของไฟล์อื่นไม่เปลี่ยน โดยไม่ต้องรันทดสอบพฤติกรรมที่ไม่ได้เปลี่ยนซ้ำ

หากเปลี่ยนข้อมูลจริง ต้องตรวจ local input ที่ประกาศไว้ด้วย สร้างใหม่ใน directory ใหม่ ทดลองผลลัพธ์/ความสัมพันธ์ที่ได้รับผลกระทบ และตรวจความต่างด้านความหมาย การยืนยัน determinism ต้องสร้างชุดข้อมูลภายในใหม่สองครั้งและสร้าง public projection สองครั้ง โดยผลตรงกันทุก byte รายงานเฉพาะการตรวจที่ทำจริง การ rebuild สำเร็จครั้งเดียวไม่ได้พิสูจน์ว่าทำการตรวจแบบสอง build รอบใหม่แล้ว

Tests/CI ใช้ fixture สังเคราะห์ขนาดเล็กหรือ fake recorder โดยบล็อกการเชื่อมต่อเครือข่ายไปยังต้นทาง การตรวจ UI ใช้ fixture บนเครื่องหรือ public artifact ที่ตรวจ hash แล้ว และครอบคลุม desktop/mobile ทุกแท็บ การเปลี่ยนหน้ารวดเร็ว สถานะไม่มีข้อมูล/ว่าง/ผิดพลาด URL/Back/focus ตัวกรองที่ถูกต้อง การไม่โหลดสื่อ และการนำทาง F1/F4 ที่ต้องไม่เสียไป

| อาการหรือข้อผิดพลาด | วิธีรับมือที่ถูกต้อง |
|---|---|
| locked input ขาดหายหรือเปลี่ยนไป | จัดหา bundle ที่ประกาศไว้ หรือเตรียม lock ใหม่ที่ผ่านการตรวจทาน ห้ามดาวน์โหลด “latest” ภายใน builder หรือผ่อนการตรวจ hash |

| hash ของ comparison/approval ล้าสมัย | ตรวจทาน bytes ชุดใหม่และบันทึกการยอมรับที่ผูกกับข้อมูลอย่างถูกต้อง ห้ามคัดลอกเพียง status flag |

| revision ขัดแย้งหรือ hash ของ artifact ไม่ตรง | โหลด revision ปัจจุบันใหม่ หรือตรวจความสอดคล้องของ publication ห้ามปนไฟล์ candidate กับไฟล์ที่ใช้งานอยู่ |

## ขอบเขตการ commit

commit ของ pipeline เต็มอาจมีหลาย module, tests และ configuration แบบมีเวอร์ชันที่ต้องเก็บไว้ คำว่า “pipeline เต็ม” หมายถึง implementation ที่รองรับการทำงานตั้งแต่ต้นจนจบ ไม่ใช่ไฟล์ Python เพียงไฟล์เดียวหรือการลบประวัติที่ใช้ตรวจสอบย้อนหลัง

ขอบเขต dependency ไม่ได้จบที่ directory โค้ด/config/tests ของ F2 contract ของ public stage ใช้การตรวจ media prefix และเพดานขนาด workspace ที่อนุมัติจาก `app/publication.py` ของระบบกลาง โดยมี regression tests ใน `tests/test_publication.py` เมื่อตัดสินใจเลือกไฟล์สำหรับ commit ของ pipeline ต้องรวมการเปลี่ยนแปลงที่จำเป็นเหล่านี้ด้วย อย่าให้ commit เผลอพึ่งการแก้ serving/UI ที่ยังไม่ได้ stage และไม่เกี่ยวกับงาน

ไม่ใส่หลักฐานดิบ การตัดสินใจส่วนตัว ชุดข้อมูลภายใน ผลลัพธ์ชั่วคราว หรือ secrets ลง Git แยกงาน UI/API ที่ไม่เกี่ยวข้องออก เว้นแต่การเชื่อมส่วนนั้นจะอยู่ในขอบเขต commit ที่ตกลงไว้ ตรวจชุดไฟล์ที่เลือกจริง ไม่ใช่ตรวจเพียง working tree ใหญ่ที่มีงานปนกัน การ commit โค้ดหรือเอกสารไม่จำเป็นต้องเผยแพร่ dataset ใหม่ การ commit, push, activation บนเครื่อง และ deployment ยังเป็นการกระทำที่ต้องได้รับอนุญาตแยกจากกัน

| รายการ | แหล่งอ้างอิงหลัก / ข้อมูลฐานที่ใช้อยู่ |

| Logical release ID | `f2-dashboard-snapshot-v3` |

API/UI และ local publication ที่ยอมรับแล้วมี implementation พร้อมใช้งาน public manifest ปัจจุบันระบุรายละเอียด 21,318 รายการ และ serving entries ของ F2 จำนวน 39 รายการ K05 มีผู้ประกอบการ 3,884 ราย โดยคงขอบเขตการตรวจทาน identity ของ C08 จากรอบก่อน จำนวนเหล่านี้มีอยู่แล้วก่อนนำชุดแก้ความสัมพันธ์มาใช้ เป็นข้อเท็จจริงเฉพาะ revision ไม่ใช่เป้าหมายที่ต้องบังคับให้หลักฐานรอบใหม่ได้เท่ากัน

manifest, contract, receipt และ hash ของ artifact ที่ใช้อยู่ร่วมกันระบุ public revision ที่ commit ไว้ logical release ID อาจใช้ร่วมกันในหลาย candidate ย้อนหลัง ให้ใช้ **manifest SHA-256** แทนการใช้ release ID อย่างเดียวเมื่อต้องการระบุ bytes ที่แน่นอน `local_promotion` บันทึกการอนุมัติ local publication แยกต่างหาก ค่า `deployment_approved=false` เป็น metadata ของขอบเขตการอนุมัติ ไม่ใช่กลไกป้องกัน deployment ขณะทำงาน

publication ที่แก้ MRU/RINMP แล้วเป็นฐานรุ่นที่ commit อยู่ manifest SHA-256 คือ `6b8afc539708cc97cacebd77c5feda306b350e005f4973c705a864f6d21af149` และ release digest ของ receipt สำหรับ workspace ทั้งชุดคือ `412b90d9f66e90bb33de66817d77bac16a6b0aae22bdc73297236b0260859416` การ rebuild ในอนาคตถือเป็น candidate ใหม่ที่ต้องตรวจทานและอนุมัติ local promotion แยก ไม่ใช่การ refresh ข้อมูล serving อัตโนมัติ

**หลักฐานการ activation ย้อนหลัง (2026-09-22):** การสร้าง promotion ซ้ำอย่างอิสระและการตรวจ publication ที่นำมาใช้ผ่านแล้ว โดยคงทั้งไฟล์ข้อมูล contract และ serving entries ที่ไม่ใช่ F2 ไว้ การตรวจ repository หลัง activation รอบนั้นบันทึกผลผ่าน 978 tests, ข้าม 9 tests และคำเตือนเรื่องการเลิกใช้ส่วนประกอบของ dependencies 2 รายการ นี่คือผลของการรันครั้งนั้น ไม่ใช่คำรับรองผลของชุดทดสอบปัจจุบัน และการอ่านคู่มือนี้ก็ไม่ได้เท่ากับตรวจรอบใหม่ หลักฐานการยอมรับและการรักษาข้อมูลเดิมอยู่ที่ `data/runtime/f2/checkpoints/f2-c08-corrected-local-promotion-20260922T082257Z/`

payload ปัจจุบันยังคง `private_revision_id=f2-dashboard-snapshot-v3-c02-map-accepted-v1` จึงใช้ข้อความนี้อย่างเดียวระบุ bytes ปัจจุบันที่แก้ C08 แล้วไม่ได้ เช่นเดียวกัน คำว่า `review` ในชื่อ configuration ไม่ได้บอกว่าได้รับการยอมรับหรือไม่ ต้องตรวจ manifest ที่แน่นอนและการผูกกับ promotion ที่ยอมรับแยกต่างหากตามด้านบน configuration แบบเต็มอื่น ๆ รวมถึง configuration แผนที่ C02 เดิมและ candidate C08 รุ่นก่อน ยังคงเป็นข้อมูลย้อนหลังหรือทางเลือกสำหรับการตรวจทาน ไม่ใช่ค่าเริ่มต้นหลายชุดที่แข่งขันกัน ต้องรักษา configuration และหลักฐานเหล่านั้นไว้

## ข้อสรุปเดิมและหลักฐานย้อนหลัง

### ข้อสรุปด้านแหล่งข้อมูลและฟิลด์ที่ยังใช้บังคับ

การตรวจแหล่งข้อมูลเมื่อ 2026-09-11 ยอมรับข้อมูล AtLocal เจ็ด dataset (ระเบียนต้นทาง 2,475 แถว) และ iCommunity/AppTech เจ็ด dataset (ระเบียนต้นทาง 5,592 แถว) โดยมีเงื่อนไข canonical evidence run คือ `raw/f2/f2_cultural_market_civil/20260825T070510Z/` และ `raw/f2/f2_icommunity/20260825T143637Z/` ตามลำดับ bundle หลังยังเก็บ assertion ของที่ตั้งและ manifest ที่ระบุที่มาไว้ด้วย แต่ไม่ได้แอบนับเพิ่มเข้าไปในจำนวนเจ็ด dataset ที่ตรวจทาน

ข้อมูลผลิตภัณฑ์จากช่องทางต่าง ๆ ของ AtLocal ซ้อนกันอยู่: observation ของรายการ 2,426 รายการถูกตรวจเทียบและจัดเป็น identity ผลิตภัณฑ์ชั่วคราวภายในแหล่งเดียว 2,027 รายการ ไม่ใช่ยอด K07 ขั้นสุดท้ายที่รวมทุกแหล่ง แถวราคา 0 จำนวน 2,097 แถวไม่ได้หมายความว่าผลิตภัณฑ์แจกฟรี และแถวบนแผนที่ที่ไม่มีชื่อ 78 แถวก็ไม่ใช่เหตุให้สร้าง identity ผลิตภัณฑ์ขึ้นเอง รหัสร้านค้าของแพลตฟอร์ม marketplace ไม่ใช่รหัสผู้ขายภายในแหล่งข้อมูลนั้น ความครบถ้วนตรวจเทียบกับ snapshot ที่เก็บมา ไม่ได้ยืนยันอย่างอิสระว่าเก็บครบประชากรทั้งหมดของต้นทาง

iCommunity/AppTech ต้องรักษาความต่างระหว่างจำนวนนวัตกรที่รายงาน 4,666 คนกับ source ID ไม่ซ้ำ 4,660 ตัวไว้ ไม่สร้างคนเพิ่มหกคน `source_key` ใช้แยก observation ไม่ใช่เอนทิตีที่ resolve แล้ว source ID ที่ซ้ำ แถวพื้นที่ และกลุ่มที่ซ้อนกันไม่ใช่หน่วยนับเพิ่มเติม ระดับความพร้อม 8–9 เป็นผลคำนวณที่ผ่านการตรวจทานบนนวัตกรรมที่ resolve แล้ว ไม่ใช่การนับแถวรายการ และยังไม่เผยแพร่ profile token พิกัดบุคคล หรือคะแนนพัฒนาการ

ผลตรวจในอดีตที่เข้าถึงข้อมูลสาธารณะได้ ยืนยันเพียงการเข้าถึงทางเทคนิค ไม่ได้ตัดสินเรื่องสิทธิ์การใช้ข้อมูลหรือรับประกันว่าจะเข้าถึงได้ในอนาคต การอนุญาตแหล่งข้อมูลครั้งแรกที่เน้นข้อมูลรวมไม่ได้อนุมัติฟิลด์รายละเอียดไปด้วย การตัดสินใจด้านฟิลด์ C02 และ local promotion ที่อธิบายด้านบนเป็นส่วนขยายที่อนุมัติแยกและมีขอบเขตเฉพาะ ไม่มีรายการใดอนุญาตให้เผยแพร่ข้อมูลดิบหรือ deploy

### ตำแหน่งหลักฐาน

เก็บ configuration, lock, การตัดสินใจ และหลักฐาน runtime ที่ Git ignore ไว้ ณ พาธเดิมตามที่บันทึก หลักฐานที่ผูกด้วย hash ต้องไม่ถูกเปลี่ยนชื่อ เขียนทับ หรือ “จัดระเบียบใหม่” ไปพร้อมกับการแก้เอกสาร

ชุดข้อมูลภายใน comparison, public projection และ promotion bundle แบบ immutable ที่ตรงกันยังอยู่ใน directory ของแต่ละ revision รุ่น C02 province-review/province-accepted ก่อนหน้านี้เก็บประวัติการเปลี่ยนจากระดับประเทศอย่างเดียวมาเป็นตัวกรองจังหวัดที่ผูกกับบุคคล ส่วนรุ่นแผนที่เพิ่มเฉพาะแผนที่ข้อมูลรวมที่ได้รับอนุมัติแยก หลักฐาน runtime อาจไม่มีใน clean clone ให้ขอผ่านกระบวนการจัดการหลักฐาน/ตรวจทานที่กำหนด ไม่ใช่นำหลักฐานนั้นมาใส่ในเอกสารสาธารณะ

configuration ของ checkpoint ย้อนหลัง K12, identity, Phase 5 และ Phase 6 ไม่ใช่จุดเริ่ม build ที่ระบบรองรับอีกต่อไป งานของแต่ละส่วนทำอยู่ใน pipeline เต็มแล้ว regression test สำหรับการปฏิเสธ profile ที่ไม่ครบยังเก็บ `config/f2_pipeline/phase6-checkpoint.json` ไว้ใน Git ส่วนไฟล์ checkpoint/configuration ย้อนหลังอื่นอาจมีเฉพาะใน workspace ของนักพัฒนาที่ทำงานเดิม หรือในชุดหลักฐานที่เก็บรักษาไว้ ไม่ได้มากับ clean clone ใช้ `git ls-files config/f2_pipeline` เพื่อแยก configuration ที่ติดตามใน Git ออกจากประวัติบนเครื่อง

รักษาไฟล์ต้นฉบับที่เก็บไว้ตามพาธที่บันทึก ข้อนี้ไม่ได้หมายความว่าต้องเพิ่มไฟล์ย้อนหลังทั้งหมดบนเครื่องเข้า PR หรือต้องลบไฟล์เหล่านั้น configuration แบบเต็มรุ่นเก่า รวมถึงกรณีรองรับ `C02_BROADER` ในอดีต เป็นข้อมูลสำหรับสร้างซ้ำ/อ้างอิง ไม่ใช่เหตุให้นำตัวชี้วัดนั้นกลับมาใน publication ปัจจุบัน หากงานจำเป็นต้องใช้หลักฐานย้อนหลังที่ขาดอยู่ ให้ขอจากผู้ดูแลที่รับผิดชอบ
