# คู่มือนักพัฒนา F2: Dashboard, data pipeline และการเผยแพร่

ฉบับภาษาอังกฤษ: [F2 developer guide](f2.md)

F2 (ฝ่าย 2) คือส่วนหนึ่งของ Dashboard สำหรับสำรวจหลักฐานเกี่ยวกับบุคคล นวัตกรรม ธุรกิจ สินทรัพย์ทางวัฒนธรรม และกิจกรรมของโครงการ ระบบรวม snapshot จากแหล่งข้อมูลแปดแหล่งเป็นตัวชี้วัดหลัก 14 ตัว และตัวชี้วัดที่เกี่ยวข้องอีกเจ็ดตัวซึ่งเรียกว่า **ตัวชี้วัดประกอบ (companions)** ผู้ใช้สำรวจผลลัพธ์ระดับประเทศ/จังหวัด รายการ รายละเอียด และข้อจำกัดของแหล่งข้อมูลได้ ตัวชี้วัดบางตัวไม่มีผลลัพธ์เพราะหลักฐานไม่เพียงพอ นี่เป็นผลลัพธ์ที่ตั้งใจไว้ ไม่ใช่ Dashboard ที่เสีย

งานมีสองแบบ:

- **งานแอปพลิเคชัน:** เปลี่ยนวิธีที่ UI หรือ API แสดงข้อมูลที่เผยแพร่แล้วใต้ `data/public/f2/` ไม่ต้องใช้หลักฐานส่วนตัวและไม่ต้องรัน pipeline
- **งานข้อมูล:** รัน pipeline (`tools/f2/`) กับ snapshot ใหม่ ตรวจทานส่วนที่ระบบตัดสินเองไม่ได้ แล้วเผยแพร่ release ใหม่หลังเจ้าของข้อมูล sign-off

Pipeline ทำงานแบบ **offline** อ่าน snapshot ที่เก็บมาแยกต่างหาก ไม่ดึงข้อมูลจากเว็บไซต์ต้นทางเอง (LLM judge เป็นขั้นตอนเดียวที่ต่อเครือข่ายและมีค่าใช้จ่าย และรันเฉพาะเมื่อสั่ง) รันซ้ำกับ snapshot และการตัดสินชุดเดิมจะได้ผลเหมือนเดิม

### รัน Dashboard ในเครื่อง

ใช้ Python 3.12 ขึ้นไปกับ virtual environment ที่ติดตั้ง dependency ของ repository แล้ว ทำตาม [CONTRIBUTING: เริ่มใช้งาน](../CONTRIBUTING.md#เริ่มใช้งาน) สำหรับการตั้งค่าครั้งแรก แล้ว activate environment:

```bash
# macOS/Linux (Bash หรือ zsh)
source .venv/bin/activate
```

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

รันคำสั่งจาก root ของ repository ค่า development เริ่มต้นใช้ SQLite ในเครื่องที่ `data/runtime/dashboard.sqlite` ตรวจ `.env` ก่อนทุกครั้ง คำสั่ง development ต้องไม่ชี้ไปที่ฐานข้อมูล production

```bash
python -m app.cli init-db
python -m app.server
```

เปิด `http://localhost:8000` แล้วเลือก **ฝ่าย 2** เอกสาร API อยู่ที่ `http://localhost:8000/docs` และ `http://localhost:8000/api/public/v1/f2/overview` คืนภาพรวมระดับประเทศ ตอนเริ่มระบบจะตรวจไฟล์สาธารณะที่ commit ไว้และโหลดเข้าฐานข้อมูลสำหรับให้บริการในเครื่อง ไม่ได้รัน pipeline หรือดาวน์โหลดข้อมูลใด ๆ ถ้าการตรวจไม่ผ่านให้หาสาเหตุ ห้ามข้ามการตรวจ

### ขอบเขตที่ต้องจำ

- Dashboard อ่าน **ไฟล์ที่เผยแพร่แล้ว** เท่านั้น ไม่อ่าน raw snapshot ฐานข้อมูลของ pipeline หรือไฟล์การตัดสิน
- การแก้โค้ดแอปพลิเคชันไม่เปลี่ยนสิ่งที่ตัวชี้วัดนับ และไม่เผยแพร่ฟิลด์ใหม่
- การสร้าง candidate, การ sign-off ของเจ้าของข้อมูล, การ promote, การ commit, การ push และการ deploy เป็นคนละขั้นตอน การ merge เข้า `main` อาจทำให้ Railway deploy ทันที ดู [publication workflow](publication-workflow.md)
- ห้าม commit raw snapshot, ไฟล์การตัดสิน, ฐานข้อมูลของ pipeline, candidate หรือ secret ไฟล์การตัดสินมีชื่อบุคคล จึงเก็บไว้ในเครื่องเท่านั้น

## Pipeline

```text
raw snapshot (data/runtime/f2/raw/<source_id>/<run_id>/)
  -> Clean    cleaner หนึ่งตัวต่อแหล่ง -> ตาราง entity (innovations, people, operators, offerings, ...)
  -> Resolve  การตัดสินที่ตรวจทานแล้ว, กฎ, แล้ว LLM judge (ถ้าสั่ง) -> entity; ที่เหลือเข้าคิวรอตรวจ
  -> Measure  SQL: แต่ละตัวชี้วัดนับ entity ใด ในจังหวัดใด; ยอดรวมจากแหล่งพร้อมส่วนประกอบ
  -> Publish  data/public/f2 + contract + การตรวจ + รายงานความต่าง -> sign-off -> promote
```

ทุกขั้นเขียนผลลงไฟล์ DuckDB ไฟล์เดียวคือ `data/runtime/f2/pipeline/f2.duckdb` จึงเปิดดูผลกลางทางด้วย SQL ได้ทุกขั้น

| คำสั่ง | ทำอะไร | เวลา |
|---|---|---|
| `python -m tools.f2 clean` | อ่าน run ล่าสุดของแต่ละแหล่งและสร้างตาราง entity ใหม่ | ~45 วินาที |
| `python -m tools.f2 resolve` | รวม record เป็น entity แล้วพิมพ์ต่อชนิด: จำนวน entity, คู่ที่ตัดสินแล้ว, คู่ที่รอตรวจ, ปัญหาของการตัดสิน | ~30 วินาที |
| `python -m tools.f2 measure` | คำนวณ 21 ตัวชี้วัดและพิมพ์ค่าระดับประเทศ | ไม่กี่วินาที |
| `python -m tools.f2 judge` | แสดงสิ่งที่จะถาม LLM judge สำหรับคู่ที่รอตรวจ (ไม่มีค่าใช้จ่าย) ใส่ `--send` เพื่อส่งจริง (มีค่าใช้จ่าย) | — |
| `python -m tools.f2 publish` | สร้าง release candidate ที่ตรวจแล้วพร้อมรายงานความต่าง | ~35 วินาที |
| `python -m tools.f2 publish --promote <candidate>` | ติดตั้ง candidate ที่ sign-off แล้วเข้า repository | ~1 นาที |

## การอัปเดตข้อมูล

1. **เอา snapshot ใหม่มา** ดึง run ด้วย `python tools/evidence_pull.py <source_id>` (ดู [evidence storage](evidence-storage.md)) แล้ววางแต่ละ run ไว้ที่ `data/runtime/f2/raw/<source_id>/<run_id>/` Clean จะอ่านโฟลเดอร์ run ที่ใหม่ที่สุดของแต่ละแหล่งเสมอ
2. **รัน Clean, Resolve และ Measure:**
   ```bash
   python -m tools.f2 clean && python -m tools.f2 resolve && python -m tools.f2 measure
   ```
3. **อ่านสรุปของ Resolve** การตัดสินผูกกับรหัส record ของแหล่ง คู่ที่ตรวจแล้วจึงยังคงตัดสินแล้ว งานใหม่เกิดเฉพาะจาก record ที่ใหม่หรือเปลี่ยนไป ดู:
   - *waiting for review*: คู่ที่กฎตัดสินไม่ได้ (ยังแยกกันจนกว่าจะตัดสิน)
   - *decision issues*: การตัดสินที่ record หายไปหรือขัดแย้งกันเอง (ตาราง `decision_issues`)
4. **ถาม LLM judge** เกี่ยวกับคู่ใหม่ที่รอตรวจ (ถ้าต้องการ มีค่าใช้จ่าย ดู[ด้านล่าง](#llm-judge)) แล้วรัน `resolve` และ `measure` อีกครั้ง
5. **ตรวจทาน** ส่วนที่เหลือและเพิ่มการตัดสิน (ดู [การตัดสินที่ตรวจทานแล้ว](#การตัดสินที่ตรวจทานแล้ว)) แล้วรัน `resolve` และ `measure` อีกครั้ง
6. **ตรวจตัวชี้วัด** เทียบค่าที่พิมพ์ออกมากับค่าที่เผยแพร่อยู่ ทุกการเปลี่ยนแปลงต้องอธิบายเหตุผลได้
7. **เผยแพร่** (ดู [การเผยแพร่](#การเผยแพร่))

สิ่งที่ผู้ตรวจพบในข้อความ (ธุรกิจ สินค้า บุคคล และกิจกรรม) จะถูกตรวจซ้ำกับ snapshot ใหม่ทุกครั้ง ถ้าข้อความอ้างอิงไม่อยู่ใน record แล้ว แถวนั้นจะถูกทำเครื่องหมาย (`details.quotes_missing`) และต้องตรวจใหม่

## การตัดสินที่ตรวจทานแล้ว

ไฟล์การตัดสินอยู่ใน `data/runtime/f2/decisions/` ผูกกับ `(source, record_id)` จึงใช้ได้ต่อเมื่ออัปเดตข้อมูล ไฟล์เหล่านี้อยู่ในเครื่องเท่านั้น (มีชื่อบุคคล) ควรสำรองไว้ในที่ส่วนตัว

| ไฟล์ | เก็บอะไร | ใครเขียน |
|---|---|---|
| `matching.json` | การตัดสินว่าเหมือน / ต่าง / ไม่แน่ใจ ระหว่างกลุ่ม record ต่อชนิด entity (รวมกลุ่มสินค้า) | ผู้ตรวจ |
| `extractions.json` | ธุรกิจ สินค้า บุคคล และกิจกรรมที่พบในข้อความ พร้อมข้อความอ้างอิง | ผู้ตรวจ |
| `parsing.json` | การแก้วิธีอ่านฟิลด์ของแหล่ง | ผู้ตรวจ |
| `counting.json` | record ที่ตัวชี้วัดไม่นับ พร้อมเหตุผล (เช่น รายการสินค้าแบบรวมที่ใช้เป็นหลักฐานของกลุ่มสินค้าเท่านั้น) | ผู้ตรวจ |
| `judge.json` | คำตอบของ LLM judge เก็บตามคู่และ prompt | `python -m tools.f2 judge --send` |

การตัดสินใน `matching.json` ระบุกลุ่มของ record: `same` รวมทุก record เข้าด้วยกัน `different` และ `unsure` แยกทุก record ของกลุ่มหนึ่งออกจากกลุ่มอื่น (`unsure` คือตรวจแล้วแต่หลักฐานไม่พอ จะไม่ถามซ้ำ) การตัดสินที่ตรวจทานแล้วชนะกฎและ judge เสมอ การเชื่อมที่จะรวม record ที่ต้องแยกกันจะไม่ถูกใช้และจะถูกรายงาน

กฎแต่ละชนิดโดยย่อ: นวัตกรรมและสินค้าแยกด้วยกฎ และเข้าคิวเมื่อไม่ชัด ธุรกิจรวมกันเมื่อแกนของชื่อ (ชื่อที่ตัดคำทั่วไป สถานที่ และหมายเลขกลุ่มออก) ตรงกันในพื้นที่เดียวกัน หรือชื่อมีลักษณะเฉพาะและไม่ขัดแย้งเรื่องพื้นที่ บุคคลรวมกันเฉพาะเมื่อชื่อเต็มที่ normalize แล้วตรงกันและหน่วยงานเข้ากันได้หรือมีผลงานร่วมกัน (ไม่ส่งชื่อบุคคลให้ LLM) กิจกรรมและรายการวัฒนธรรมใช้การจับคู่แบบกำหนดแน่นอน รายละเอียดกฎอยู่ที่ต้นไฟล์ `tools/f2/resolve/<kind>.py`

### LLM judge

`python -m tools.f2 judge` แสดงรายการคำขอที่จะส่งสำหรับคู่นวัตกรรมและสินค้าที่รอตรวจ โดยไม่มีค่าใช้จ่าย `--send` จะส่งจริง (ต้องมี `OPENROUTER_API_KEY` ใน environment, `--budget` หยุดเมื่อใช้ถึงจำนวน USD ที่กำหนด, `--entity` จำกัดชนิด) กฎที่ห้ามผ่อนปรน:

- ส่งคำขอไปยังผู้ให้บริการแบบ zero-data-retention และปฏิเสธการเก็บข้อมูล
- ปิดชื่อบุคคล อีเมล และเบอร์โทรก่อนส่ง คำขอที่ยังมีชื่อเต็มที่รู้จักจะไม่ถูกส่ง
- ใช้คำตอบอัตโนมัติเฉพาะชนิดที่อยู่ใน `judge.APPLIED` (ปัจจุบัน: นวัตกรรมและสินค้าที่ตอบว่า *ต่างกัน* ด้วยความมั่นใจสูง) คำตอบอื่นเป็นข้อเสนอที่เก็บไว้กับคู่นั้น (`match_pairs.judge`) ให้ผู้ตรวจพิจารณา

การรันที่มีค่าใช้จ่ายต้องได้รับอนุมัติจากเจ้าของข้อมูล

## การเผยแพร่

1. **สร้าง candidate:** `python -m tools.f2 publish` จะเขียน `data/runtime/f2/publish/<time>/` ซึ่งจัดวางเหมือน repository:
   - `data/public/f2/`: ภาพรวม ข้อมูลพื้นที่ ไฟล์ต่อหัวข้อ และไฟล์รายละเอียดที่จำกัดขนาด
   - `config/publication_contracts/f2_dashboard.json`: contract การเผยแพร่ของ F2 ที่สร้างใหม่สำหรับไฟล์ชุดนี้ (รายการไฟล์ จำนวน record ฟิลด์ชื่อ/สถานที่ที่อนุญาต สูตรตัวชี้วัดจาก `config.json`)
   - `data/public/serving_manifest.json` ที่แทนรายการของ F2 แล้ว และ receipt ใหม่
   - ไฟล์สาธารณะและ contract อื่นทั้งหมด (hard link) เพื่อให้การตรวจการเผยแพร่ของ repository ตรวจ candidate ทั้งชุดได้ ผลอยู่ใน `validation.json`
2. **อ่านรายงานความต่าง** `diff/diff.md` (ค่า จังหวัด entity ที่นับ รายละเอียด โครงสร้าง) เทียบกับไฟล์ที่เผยแพร่อยู่ อธิบายทุกการเปลี่ยนแปลง
3. **Sign-off ของเจ้าของข้อมูล** เจ้าของข้อมูลอนุมัติ candidate เป็นข้อมูลสาธารณะชุดถัดไป ก่อนขั้นนี้ไม่มีอะไรสาธารณะเปลี่ยน
4. **Promote:** `python -m tools.f2 publish --promote <candidate>` คัดลอก `data/public/f2` contract และ serving manifest เข้า repository ทำเครื่องหมายว่า F2 manifest อนุมัติแล้ว เขียน receipt ใหม่ และตรวจ public workspace ทั้งชุด
5. **ตรวจและ commit:** รัน `python -m app.cli check` แล้ว commit release (ไฟล์สาธารณะ contract serving manifest receipt) บน feature branch และเปิด PR การ push และ deploy เป็นไปตาม [publication workflow](publication-workflow.md)

รหัส entity (`inn_…`, `per_…`, `op_…`, `fam_…`, `cul_…`, `act_…`) สร้างจาก key ของ record ต้นทางที่เล็กที่สุดของ entity `(source, record_id)` จึงคงเดิมเมื่ออัปเดตข้อมูล เว้นแต่ record นั้นหายไปหรือมี record ที่เล็กกว่าเข้ามารวม ลิงก์รายละเอียดที่บันทึกไว้ (`?f2detail=<id>`) จึงมักยังใช้ได้

สิ่งที่ตัวเผยแพร่รับประกัน:

- เขียนเฉพาะฟิลด์ที่ Dashboard แสดง และเฉพาะชนิดฟิลด์ที่เคยเผยแพร่แล้ว การเพิ่มชนิดฟิลด์ใหม่ต้องได้รับอนุมัติจากเจ้าของข้อมูล
- ข้อความอิสระผ่านการลบข้อมูลติดต่อของ repository (`app/privacy.py`) ข้อความที่การตรวจการเผยแพร่ (`app/publication.py`) ยังจะตรวจพบ เช่น ที่อยู่ ช่องทางติดต่อที่มีป้ายกำกับ หรือข้อมูลสุขภาพหรือการเงินของบุคคล จะไม่แสดง ชื่อที่แสดงไม่ได้จะปรากฏเป็น *Title withheld pending review*
- ลิงก์ต้องผ่านกฎ URL ของการตรวจการเผยแพร่และเป็นของแหล่งนั้น สื่อเป็นลิงก์อ้างอิงเท่านั้น ไม่ดึงมาหรือเก็บไว้เอง
- ชื่อบางรายการที่การตรวจความเป็นส่วนตัวจะเข้าใจผิดว่าเป็นที่อยู่หรือช่องทางติดต่อ ได้รับการตรวจแล้วว่าเผยแพร่ได้ (บ้านเก่าที่ตั้งชื่อตามบ้านเลขที่ นวัตกรรมที่ตั้งชื่อตามช่อง LINE) อยู่ใน `config.json` (`reviewed_labels`) ตาม record ต้นทาง ตัวเผยแพร่จะเพิ่ม field context ให้แต่ละรายการใน contract

- ตัวชี้วัดตอบเฉพาะตัวกรองใน `supported_filters` และ `permitted_combinations` ตัวกรองที่ไม่รองรับคืนผล *unavailable* พร้อมเหตุผล ไม่ยืมค่าระดับประเทศมาแทน ค่าระดับประเทศหรือภูมิภาคตามแหล่งอาจแสดงข้าง ๆ โดยติดป้ายว่าเป็นบริบท
- นับ entity ครั้งเดียวหลังรวม entity ที่มีสถานที่ในสองจังหวัดนับในแต่ละจังหวัดและนับครั้งเดียวในระดับประเทศ ค่ารายจังหวัดจึงบวกกันไม่ได้ entity ที่ไม่มีสถานที่นับเฉพาะระดับประเทศ
- ศูนย์ ไม่ทราบ และไม่มีผล แตกต่างกัน จังหวัดที่แหล่งไม่ได้รายงานคือไม่มีผล ไม่ใช่ศูนย์
- ภูมิภาคตามแหล่งของ Learning dashboard เป็นคนละระบบกับจังหวัดและภูมิภาคของ Dashboard
- ยอดรวมจากแหล่งบวกกันภายในมิติเดียวเท่านั้น มิติธุรกิจสี่มิติของ Learning คือมุมมองสี่แบบของยอดเดียว ไม่ใช่สี่ยอด
- เงินใช้การคำนวณทศนิยม การแสดงผลปัดเศษ แต่เก็บค่าที่แน่นอนไว้

- **ผลลัพธ์:** `value` ที่เป็นตัวเลขหรือ null, `display_value`, `unit`, `status`, `availability`, `requested_filters` / `applied_filters` และ `unavailable_reason` ผู้ใช้ข้อมูลต้องไม่แปลงข้อความที่แสดงกลับเป็นตัวเลขหรือนับรายการเพื่อหาค่า

| `GET /overview` | ผลระดับประเทศหรือ `province=<code>` พร้อมผลที่ไม่มีค่าแบบชัดเจน |
| `GET /map?measure=<id>` | ช่องรายจังหวัดและคำอธิบายแผนที่ของตัวชี้วัดที่รองรับจังหวัด |
| `GET /topics/{topic_id}` | ผล ตัวกรอง ที่มา และรายการหนึ่งหน้าของตัวชี้วัดและขอบเขตที่เลือก |
| `GET /topics/{topic_id}/details/{entity_id}?measure=<id>` | รายละเอียดหนึ่งรายการที่อยู่ในตัวชี้วัดและขอบเขตนั้น |

Query parameter ที่ route และตัวชี้วัดรองรับ: `province`, `category`, `source_level`, `source_region`, `component`, `source_dimension`, `q`, `sort`, `limit`, `offset`, `revision`

- รายการค่าเริ่มต้น 25 รายการ สูงสุด 100 การค้นหาตรงกับชื่อรายการเท่านั้น `result` ของ KPI ไม่ถูกคำนวณใหม่จากรายการ
- Response มี revision (hash ของ manifest) การส่ง `revision` ป้องกันการปนข้อมูลต่าง release entity ที่ไม่รู้จักหรือไม่ได้อยู่ในตัวชี้วัดคืน 404 ตัวกรองไม่ถูกต้องคืน 422 revision เก่าคืน 409 ข้อมูลเผยแพร่ที่ขาดหรือไม่สอดคล้องคืน 503
- ETag เปลี่ยนตาม revision และ request response ต้อง revalidate (`public, max-age=0, must-revalidate`)

Dashboard มีสามแท็บ: **ภาพรวม**, **รายการ**, **ที่มาและข้อจำกัด** ตัวชี้วัด ขอบเขต ตัวกรอง การค้นหา หน้า และรายละเอียดที่เปิดอยู่ถูกเก็บใน URL สื่อเป็นลิงก์เท่านั้น ไม่โหลดอัตโนมัติ

## การตรวจสอบและการแก้ปัญหา

ก่อนเปิด PR ให้รันชุดตรวจเต็ม:

```bash
python -m app.cli check
```

คำสั่งนี้รัน compile, pipeline validation, publication validation, public-repository boundary check และ pytest ใส่ `--skip-tests` เพื่อตรวจรอบเร็วระหว่างทำงาน

| การเปลี่ยนแปลง | การตรวจที่เกี่ยวข้อง |
|---|---|
| กฎการเผยแพร่/ความเป็นส่วนตัว | `tests/test_publication.py`, `tests/test_field_contexts.py`, `tests/test_public_artifacts.py` |
| API, ตัวกรอง, revision ของ F2 | `tests/test_f2_api.py`, `tests/test_f2_c02_api_contract.py` |
| การแสดงผล F2 | `tests/test_f2_detail_presentation.py`, `tests/test_ui_coverage.py` และตรวจในเบราว์เซอร์ |

`tests/test_f2_api.py` รันกับไฟล์ที่เผยแพร่อยู่และตรึงค่าบางค่าไว้ (จังหวัดของรายการ K12 รายการแรก รหัสของกลุ่มสินค้าราคา 0 และรายการที่ซ่อนชื่อ) เมื่อ release ใหม่เปลี่ยนค่าเหล่านั้น ให้แก้ค่าที่ตรึงไว้ใน commit เดียวกับ release

| อาการ | สิ่งที่ต้องทำ |
|---|---|
| `no raw snapshot under …` | วางโฟลเดอร์ run ของแหล่งนั้นไว้ใต้ `data/runtime/f2/raw/<source_id>/` |
| Resolve รายงาน decision issues | อ่าน `decision_issues`: record ของการตัดสินหายไปหรือการตัดสินสองรายการขัดกัน ให้แก้ที่การตัดสิน ไม่ใช่ที่กฎ |
| ตัวชี้วัดเปลี่ยนโดยไม่คาดคิด | เทียบ `measure_members` กับรายการที่เผยแพร่ หา record ที่ย้ายและเหตุผล |
| `validation.json` ไม่ผ่าน | อ่านปัญหาในไฟล์ แก้ที่ตัวเผยแพร่หรือข้อมูล ห้ามผ่อนการตรวจการเผยแพร่ |
| ไฟล์เกินขนาด | ตัวเผยแพร่จะหยุด ไฟล์รายละเอียดถูกแบ่งที่ประมาณ 3.9 MB หัวข้อต้องไม่เกิน 8 MiB |
| server ในเครื่องเริ่มไม่ได้ | ตรวจการตั้งค่าฐานข้อมูล และตรวจว่า F2 manifest, serving manifest, receipt และ contract เป็นชุดเดียวกัน (รัน `python -m app.cli check`) |
