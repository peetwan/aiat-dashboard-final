# F2: data pipeline, publication, and dashboard guide

F2 (ฝ่าย 2) uses an offline, deterministic data pipeline and a dashboard that reads only reviewed public artifacts. This is the maintained guide for the implemented system, not a phased implementation plan.

The supported builder runs the **complete pipeline**: eight pinned sources, 14 headline measures, and seven active companions. Historical partial checkpoints are not runnable. A complete pipeline does not imply complete upstream coverage: unavailable measures, uncertain identities, unknown geography, and source limitations remain explicit.

## Architecture and code map

```text
separately acquired immutable evidence + accepted review/reference inputs
    -> local file, source, run, size, and SHA-256 validation
    -> source-local observations, identities, assertions, and relationships
    -> reviewed cross-source identity and semantic resolution
    -> measure contributions, aggregate components, and filter indexes
    -> complete immutable internal release
    -> comparison and hash-bound internal review
    -> deterministic public candidate + scoped field/privacy validation
    -> separately authorized, independently verified local promotion bundle
    -> complete replacement-overlay validation and explicit local activation
    -> reviewed public artifacts -> serving database -> F2 API -> dashboard
```

Builds do not fetch upstream data, access R2, run model inference, or read old derived tables. Evidence acquisition is separate; see [evidence storage](evidence-storage.md). Canonical team-bucket evidence must not be overwritten or deleted. The repository is a public serving application, not the raw evidence lake.

The internal build does not read the frozen v2 release. The `compare` command uses that release as a migration reference. The current `project-public` interface still requires the resulting comparison and its accepted review; it does not bypass that gate for routine rebuilds. Neither v2 nor private candidate data is a web-runtime input.

### Domain terms and invariants

| Term | Meaning |
|---|---|
| Observation | One captured source record or assertion; repeated observations are not necessarily different entities. |
| Source-local identity | An identity resolved within one source and its declared grain. |
| Global identity | A reviewed identity joining compatible source-local members. |
| Assertion / relationship | A source-supported claim or connection attached to a particular subject, role and observation. |
| Eligibility | Qualification for one measure, separate from identity. |
| Contribution | One counting unit, uniquely keyed by `(measure_id, entity_id)`. |
| Membership | A supported geography/category connection used to filter a contribution. |
| Aggregate component | A reported amount with a unit, divisor and breakdown group; not an entity roster. |
| Companion | A related population or interpretation, not an amount added to its headline. |
| Internal release / public projection | The complete audit package / its explicitly reviewed public subset. |

Identity merges preserve all observations, roles, locations, assessments and conflicts. `match`, `keep_separate`, and `unresolved` are different decisions; transitive matches must not cross cannot-links or unresolved protections. Shared projects do not transfer roles, matching businesses does not merge all products, and product locations do not become seller locations.

Evidence pointers must resolve to the supporting observation, not merely an existing row in the same file. Dataset-local numeric IDs are not interchangeable: an MRU requirement owner must not acquire an innovation relationship because the two datasets share an ID. MRU requirement and child identities/ownership, RINMP declared row counts and owner IDs, and RINMP profile-to-observation ownership are validated before accepting derived output.

| K11A | Null, insufficient cluster identities | Wallet categories are not clusters. |
| K11B | Null, insufficient cluster–province evidence | Programme coverage is not cluster geography. |
| K12 | 5,141 mapped subjects | Province and category; people and cultural knowledge holders are included. |

These values describe the accepted baseline, not constants that justify changing a source result. An evidence change requires an explained, reviewed revision.

Required semantics:

- There is no year/calendar-month filter or invented time series. Fiscal/project years are context. Capture time is neither a price effective date nor proof of current availability.
- Use both `supported_filters` and `permitted_combinations` for the selected measure. Companions can differ from their headline. Prepare national and all 77 province result bundles, including explicit unavailable cells.
- Count distinct entities after joins. Internally, multiple values within a supported dimension form a union; different dimensions intersect. The UI selects national or one province, not an invented general multi-select contract.
- Unknown geography remains national-only; overlapping province memberships are nonadditive. Do not sum provincial counts to reconstruct a national result.
- Zero, unknown, missing and unavailable differ. An empty supported entity selection can mean zero qualifying records in this snapshot. Missing aggregate members, failed inputs and unsupported filters are not zero.
- Unsupported province requests must not silently return national or regional totals. Broader context, where available, is separately labelled and scoped.
- Learning source regions are a distinct scheme from dashboard regions. Shared labels do not prove equivalent boundaries.
- Aggregate queries operate within one valid breakdown group using declared amounts/divisors. Four independent Learning business marginals do not produce 1,500 businesses. K02's reported total and geographic groups need not reconcile; do not manufacture people to close a gap.
- Money uses decimal arithmetic; display rounding does not change stored amounts. Search/pagination counts do not recalculate KPIs.

## Build and review workflow

### 1. Prepare declared inputs and new output paths

Run commands from the repository root with the existing environment. The examples below create candidates, not serving data. Choose a new tag; all builder output directories must be absent. Never reuse an accepted directory or overlap evidence/review inputs.

```bash
TAG="f2-next-review"
CONFIG="config/f2_pipeline/v3-c08-identity-review-v1.json"
RELEASE="data/runtime/f2/releases/$TAG"
COMPARISON_DIR="data/runtime/f2/comparisons/$TAG"
COMPARISON_REVIEW="$COMPARISON_DIR/accepted-review.json"
STAGE="data/runtime/f2/public-projections/$TAG"
CONTRACT="$COMPARISON_DIR/staged-contract.json"
BUNDLE="data/runtime/f2/promotions/$TAG"
```

The tag distinguishes output locations; it does not mint approval or change the configuration's logical release identity. For changed evidence, definitions or field scope, prepare a new versioned configuration and review its dependencies instead of editing an existing locked configuration.

Optional input audit:

```bash
.venv/bin/python -m tools.f2_pipeline audit-inputs \
  --lock config/f2_pipeline/inputs.v3.json \
  --evidence-root data/runtime/f2/raw --review-root .
```

`audit-inputs` checks the evidence and its supported migrated review ledgers; it does not replace the full configuration-specific build and domain checks.

### 2. Build the complete internal release

```bash
.venv/bin/python -m tools.f2_pipeline build \
  --config "$CONFIG" \
  --evidence-root data/runtime/f2/raw \
  --review-root . \
  --output "$RELEASE"
```

Only `profile=full`, `complete=true`, `publication_status=internal_only` configurations are accepted. Do not try to build K12-, identity-, commerce- or aggregate-only historical checkpoints.

The internal package contains `manifest.json`, `input_manifest.csv`, `definitions.json`, `projection_policy.json`, `results.json`, `kpi_results.csv`, `companion_results.csv`, `measure_dictionary.csv`, `entity_contributions.csv`, `evidence_links.csv`, `eligibility_evidence.csv`, `province_memberships.csv`, `province_coverage.csv`, `category_memberships.csv`, `aggregate_breakdowns.csv`, `validation_checks.csv`, `table_catalog.csv`, and catalogued source/domain tables under `sources/` and `domains/`. All files, rows, keys and JSON cells are validated; identities and output ordering must be deterministic.

To inspect an internal selection without changing a release:

```bash
.venv/bin/python -m tools.f2_pipeline query \
  --release "$RELEASE" --measure K12 --filters '{}'
```

The internal query uses its own declared filter vocabulary; HTTP parameter names are documented separately below. Never edit result tables to obtain a preferred total.

### 3. Compare and obtain internal acceptance

Set `V2_REFERENCE` to the available, verified frozen `f2-dashboard-snapshot-v2` directory. This reference is required by the comparison step, not the build or serving application.

```bash
.venv/bin/python -m tools.f2_pipeline compare \
  --release "$RELEASE" \
  --reference "$V2_REFERENCE" \
  --output "$COMPARISON_DIR"
```

Review values, definitions, identities, eligibility, geography, aggregate components, detailed tables and semantic differences—not just equal headline totals. Do not force current results to match v2. The frozen v2 manifest recorded source-code drift; it is a comparison artifact, not a reproducible current-code build input.

Create `$COMPARISON_REVIEW` only from actual review. `comparison_review.py:verify_comparison_review` checks:

- `schema_version=1`, matching `release_id`, `review_status=accepted`, and `scope=internal_release_only`;
- exact `release_manifest_sha256`, `comparison_sha256`, and `reference_manifest_sha256`;
- exactly one accepted decision per material `difference_id`, with nonempty `reason` and `acceptance_basis`;
- consistency of the comparison evidence with the current release.

There is no CLI command that grants acceptance automatically. Old decisions can carry forward only where their evidence still applies, with bindings to the new bytes. Unchanged KPI totals alone are insufficient. Internal acceptance grants neither public-field acceptance nor promotion.

### 4. Project a public candidate and prepare its contract

```bash
.venv/bin/python -m tools.f2_pipeline project-public \
  --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --output "$STAGE"
```

The output is `staged_for_review`, not publication-ready. It selects fields from the internal release under the locked policy and does not write `data/public/`.

Prepare a contract candidate using the existing library seam. This writes a new file with exclusive creation; it does not replace the active contract or approve changed fields/counts.

```bash
.venv/bin/python - "$STAGE" "$RELEASE" "$CONTRACT" <<'PY'
import sys
from pathlib import Path
from tools.f2_pipeline.common import canonical_json, load_json
from tools.f2_pipeline.public_stage import make_staged_contract

stage, release, destination = map(Path, sys.argv[1:])
contract = make_staged_contract(
    stage,
    load_json(release / "definitions.json")["measures"],
    load_json(release / "projection_policy.json"),
)
with destination.open("x", encoding="utf-8", newline="\n") as stream:
    stream.write(canonical_json(contract) + "\n")
PY
```

Review the candidate contract against the existing contract and approved policy. Changes to identity counts, field contexts, output inventory or limits are reviewable changes, not automatically approved refreshes. Retain the generated contract with the candidate's evidence.

### 5. Validate the stage, respecting the existing publication

F2 is already active in this repository. The default combined `validate-public-stage` deliberately refuses a repository containing `data/public/f2/`; it will not implicitly replace it. Use the F2-only mode for a diagnostic check:

```bash
.venv/bin/python -m tools.f2_pipeline validate-public-stage \
  --stage "$STAGE" --contract "$CONTRACT" \
  --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --f2-only
```

This independently rederives the stage, verifies byte identity and the exact contract, and exercises publication validation in temporary storage. **It does not prove the complete replacement workspace fits or is ready to activate.**

For a first activation into a repository with no F2 publication, omit `--f2-only`; `--repository` can point to a prepared disposable repository. For a refresh of the current publication, follow the replacement-overlay procedure below. Do not remove the active F2 files merely to make stage validation pass.

### 6. Separately authorize and verify local promotion

Only after field/privacy/semantic review and explicit local-promotion authorization, set `DECISION` to the reviewed decision file and run:

```bash
.venv/bin/python -m tools.f2_pipeline promote-local \
  --stage "$STAGE" --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --decision "$DECISION" --output "$BUNDLE"

.venv/bin/python -m tools.f2_pipeline verify-local-promotion \
  --bundle "$BUNDLE" --stage "$STAGE" --release "$RELEASE" \
  --comparison "$COMPARISON_DIR/comparison.json" \
  --comparison-review "$COMPARISON_REVIEW" \
  --decision "$DECISION"
```

`promotion.py:_validate_decision` defines the exact schema and accepted decision IDs. The decision must bind the exact stage-manifest SHA-256, be accepted for `local_publication_only`, set `local_publication_approved=true`, and keep `deployment_approved=false`. A copied old decision with stale hashes is invalid. This trusted local review record is not a cryptographic identity check or a substitute for owner authorization.

Neither command activates files or writes the active receipt. The bundle contains the publication-ready F2 directory, contract, serving entries and attestation. Promotion changes approved publication-state metadata, not substantive identities, prices, locations or field dispositions.

Before activation:

1. Make a disposable replacement workspace containing the existing public files, contracts, catalog and serving inventory.
2. Apply the verified bundle **inside that disposable workspace**: replace the F2 directory and F2 contract, replace only `f2/` serving entries, and preserve all non-F2 entries/files.
3. Generate the overlay's receipt with `app.publication.write_receipt` and validate it with `app.publication.validate_workspace`, passing the disposable root, its contracts directory and catalog path. Check the full-workspace budget, privacy, identities, hashes and serving compatibility. F2-only validation is not a substitute.
4. Retain the reviewed decision, independent verification, preservation evidence and pre-activation control-file backups. Only then apply the separately authorized replacement locally.
5. After authorized activation, regenerate and validate the active receipt and run the repository gate:

```bash
.venv/bin/python -m app.cli publication receipt
.venv/bin/python -m app.cli publication validate
.venv/bin/python -m app.cli check
```

See [publication workflow](publication-workflow.md#f2-local-promotion) for the shared activation boundary. Do not hand-edit artifact JSON, claim acceptance by changing a status string, deploy, or push merely because a candidate or receipt validates.

## Public artifacts and approved fields

### Artifact shape

The public package has `overview.json`, `geography.json`, 14 `topics/k*.json` entries, deterministic size-bounded `details/*.json` children, and `manifest.json`. Every child is declared in the publication and serving inventories. The manifest is provenance, not an extra UI topic.

- **Overview:** all headline/companion definitions, national result cells, units, statuses, limitations, source IDs, capabilities and artifact keys.
- **Geography:** 77 canonical two-digit province codes and scoped results, supported source-region data, unknown/overlap coverage, separately labelled context and map eligibility. No fabricated province allocation.
- **Topic:** `filter_contracts`, precomputed `scopes`, `item_ids_by_measure_and_scope`, compact `items_by_id`, `details_by_id`, `detail_lookup`, `detail_artifacts`, sources and limitations. Lists and details follow the selected measure's admission index.
- **Result cell:** numeric `value` or real null, `display_value`, unit, semantic `status`, request `availability`, `scope_key`, requested/applied filters and an unavailable reason. Consumers must not recover numbers by parsing display strings or recompute them from list lengths.

Entity sections reconcile counted, publicly admitted and wholly withheld populations. Aggregate sections expose their declared component/breakdown grain, not invented person/business rosters. One detail may be shared across measures or scopes; membership still has to be checked.

### Public detail rows

Projection selects named fields; it never serializes arbitrary internal rows or `*_details_json` cells. Apply the source-specific policy, approved leaf-level [field contexts](field-contexts.md), text sanitization, provenance checks, byte limits and deterministic ordering.

| Detail population | Accepted fields and limits |
|---|---|
| K01B cultural areas and K12 mapped subjects | Labels, selected safe descriptions/history, categories, identity uncertainty, source memberships, supported administrative locations, permitted citations and selected media references. K12 includes people/knowledge holders, not just non-person places. |
| K05 operators | Labels, identity/uncertainty, memberships, safe business evidence, operator-owned administrative geography and supported offering relationships. No person-operator directory, private contacts, prices or images. |
| C08 participating businesses | Learning Area Based labels or explicit `Name unavailable`, provisional identity, own geography, participation/project/research-unit/fiscal-year context. No proof of improvement, person-assessment links, narrative profile, prices or media. |
| K07 offering families | Family labels/categories/status, preserved offering/variant children, selected descriptions, offering-owned geography, supported relationships/citations, separately attributed member prices and selected media references. |
| K03 activities | Labels, selected descriptions, explicit dates, venues, sessions, publication links and supported attribution. Source allowlists differ; sessions/publications do not add counted occurrences. |
| K04 and C04_LISTED innovations | Titles, selected descriptions, source records, readiness assertions, supported use locations and explicitly attached work attribution/organizations. Readiness is not an individual's development score. No selected prices or media. |
| C02 people | Narrow public-work attribution, qualifying assertions and reviewed province-only geography under the separate contract below. |

The original approval covered six detail measures; a separate extension accepted K01B/K12, and subsequent C02 field, geography and aggregate-map decisions extended the person projection. These are scoped decisions, not blanket publication permission for every source field.

Common rules:

- Publish an actual association, not a name or organization inferred from narrative text. Source allowlists differ even when adapters share an interface.
- Preserve the subject and role of each location. General non-C02 approved detail locations may include supported province/district/subdistrict codes/names. Unsupported levels remain unknown; street addresses and exact coordinates stay excluded. C02 is stricter: province only.
- Exclude credentials, cookies, account/profile identifiers, tokens, authentication/reset links, raw HTML/payloads, private evidence paths/locators, private contacts, and person-level health/household/financial/assessment disclosures. Removing a name does not make an individual assessment publishable.
- Withhold an unsafe field before dropping an otherwise safe detail; preserve omitted-field/child reasons. A title exception does not authorize unrelated fields.
- Public URLs must match approved source/host/path rules and retain source attribution. A portal fallback is labelled `link_scope=source`, not a record-specific link. RINMP's unregistered record API routes remain withheld; its 630 baseline listings retain source-portal citations and opaque listing identities instead.

### Prices, media, and exceptions

K07 prices are source-reported nonnegative member assertions from allowlisted AtLocal, CulturalMap and iCommunity observations. Preserve currency, parse status and snapshot context. Never collapse different member prices to one family price. Zero displays exactly **`price unspecified/source reports 0`**, never “free”. Missing sale units and effective dates remain `not_reported`; currency precision and free-text qualifiers are not inferred units. Source activity/stock flags do not prove current availability.

Media is **references only**: source-qualified HTTPS links, attribution, `source_reference_not_fetched`/reference-only status. No automatic loading, previews, prefetch, proxying, copying or hosting is authorized. CulturalMap's extra `/file-upload/` and `/gallery/` prefixes are scoped to admitted media URLs; they do not broaden ordinary source links or the generated source catalog.

The serving layer reads only reviewed public artifacts through `PublicArtifact` or the approved public-file fallback.
