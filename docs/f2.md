# F2 developer guide: dashboard, data pipeline, and publication

ภาษาไทย: [คู่มือ F2](f2-th.md)

F2 (ฝ่าย 2) is the dashboard section for exploring evidence about people, innovations, businesses, cultural assets, and programme activity. It combines eight source snapshots into 14 headline measures and seven related measures called **companions**. Users can explore national/province results, lists, details, and source limitations. Some measures are unavailable because the evidence is insufficient; that is a deliberate result, not a broken dashboard.

There are two kinds of work:

- **Application work:** change how the UI or API presents the published data under `data/public/f2/`. You need no private evidence and no pipeline run.
- **Data work:** run the pipeline (`tools/f2/`) on new source snapshots, review what it cannot decide, and publish a new release after the owner's sign-off.

The pipeline is **offline**: it reads snapshots that were captured separately and never fetches source websites (the optional LLM judge is the one networked, paid step, and it only runs when asked). Running it again on the same snapshots and decisions gives the same results.

## Getting started

### Choose the path for your task

| Task | Start here | What you need |
|---|---|---|
| Change layout, labels, navigation or detail presentation | `app/static/f2.js`, `f2-detail.js`, `f2.css`; see [API and dashboard](#api-and-dashboard) | The repository and the committed public files |
| Change API selection, filtering or response shape | `app/f2_data.py`, F2 routes in `app/main.py`, `app/api_schemas.py` | The same; run the API tests |
| Change how a source is read | `tools/f2/clean/<source>.py` | The raw snapshots under `data/runtime/f2/raw/` |
| Change matching rules | `tools/f2/resolve/<kind>.py` | The snapshots and the decision files |
| Change what a measure counts | `tools/f2/measure/members.sql` or `values.sql` | The snapshots and the decision files |
| Change dashboard text (measure names, limitations, source notes) | `tools/f2/publish/config.json` | Then publish a new release |
| Load newer snapshots | [Refreshing the data](#refreshing-the-data) | Snapshots, decision files, owner sign-off |

### Run the dashboard locally

Use Python 3.12 or later and a virtual environment with the repository's dependencies. Follow [CONTRIBUTING: getting started](../CONTRIBUTING.md#เริ่มใช้งาน) for the initial setup, then activate the environment:

```bash
# macOS/Linux (Bash or zsh)
source .venv/bin/activate
```

```powershell
# Windows PowerShell
.\.venv\Scripts\Activate.ps1
```

Run commands from the repository root. The default development configuration uses local SQLite at `data/runtime/dashboard.sqlite`; check any `.env` first so that development commands never point at a production database.

```bash
python -m app.cli init-db
python -m app.server
```

Open `http://localhost:8000` and select **ฝ่าย 2**. The API reference is at `http://localhost:8000/docs`; `http://localhost:8000/api/public/v1/f2/overview` returns the national overview. Startup validates the committed public files and loads them into the local serving database; it does not run the pipeline or download anything. Investigate a validation failure; do not bypass it.

### Boundaries

- The dashboard reads **published files** only: never raw snapshots, the pipeline database or decision files.
- Changing application code does not change what a measure counts, and does not publish new fields.
- Building a release candidate, the owner's sign-off, promoting it, committing, pushing and deploying are separate steps. Merging into `main` can trigger a Railway deployment; follow the [publication workflow](publication-workflow.md).
- Never commit raw snapshots, decision files, the pipeline database, candidates or secrets. Decision files contain personal names; they stay local.

## The pipeline

```text
raw snapshots (data/runtime/f2/raw/<source_id>/<run_id>/)
  -> Clean    one cleaner per source -> entity tables (innovations, people, operators, offerings, ...)
  -> Resolve  reviewed decisions, then rules, then (optionally) the LLM judge -> entities; the rest is queued
  -> Measure  SQL: which entities each measure counts, in which provinces; source totals with their parts
  -> Publish  data/public/f2 + contract + checks + diff report -> owner sign-off -> promote
```

Everything the stages write goes into one DuckDB file, `data/runtime/f2/pipeline/f2.duckdb`, so any intermediate result can be inspected with SQL.

| Command | What it does | Time |
|---|---|---|
| `python -m tools.f2 clean` | Reads the latest run of each source and rebuilds the entity tables | ~45 s |
| `python -m tools.f2 resolve` | Groups records into entities; prints per kind: entities, pairs decided, pairs waiting for review, decision issues | ~30 s |
| `python -m tools.f2 measure` | Computes the 21 measures; prints the national values | seconds |
| `python -m tools.f2 judge` | Shows what the LLM judge would be asked for the queued pairs (free); `--send` asks it (paid) | — |
| `python -m tools.f2 publish` | Builds a checked release candidate and a diff report | ~35 s |
| `python -m tools.f2 publish --promote <candidate>` | Installs a signed-off candidate into the repository | ~1 min |

## Refreshing the data

1. **Get the new snapshots.** Pull the runs with `python tools/evidence_pull.py <source_id>` (see [evidence storage](evidence-storage.md)) and put each run under `data/runtime/f2/raw/<source_id>/<run_id>/`. Clean always reads the newest run folder of each source.
2. **Run Clean, Resolve and Measure:**
   ```bash
   python -m tools.f2 clean && python -m tools.f2 resolve && python -m tools.f2 measure
   ```
3. **Read Resolve's summary.** Decisions are keyed by source record IDs, so reviewed pairs stay decided. Only new or changed records create new pairs. Look at:
   - *waiting for review*: pairs the rules could not decide (they stay separate until decided);
   - *decision issues*: decisions whose records disappeared or that contradict each other (table `decision_issues`).
4. **Optionally ask the LLM judge** about the new queued pairs (paid, see [below](#the-llm-judge)), then run `resolve` and `measure` again.
5. **Review** what is left and add decisions (see [Reviewed decisions](#reviewed-decisions)), then run `resolve` and `measure` again.
6. **Check the measures.** Compare the printed values with the published ones; every change should have a reason you can explain.
7. **Publish** (see [Publishing](#publishing)).

Extracted findings (businesses, products, people and activities that reviewers found in record text) are re-checked against each new snapshot: if a supporting quote is no longer in its record, the row is flagged (`details.quotes_missing`) and needs a new look.

## Reviewed decisions

Decision files live in `data/runtime/f2/decisions/`, keyed by `(source, record_id)`, so they survive refreshes. They are local only (they contain names); keep a private backup.

| File | Holds | Written by |
|---|---|---|
| `matching.json` | Same / different / unsure decisions between groups of records, per entity kind (also product families) | Reviewers |
| `extractions.json` | Businesses, offerings, people and activities found in record text, with supporting quotes | Reviewers |
| `parsing.json` | Corrections to how a source field is read | Reviewers |
| `counting.json` | Records a measure does not count, with the reason (e.g. a product-range listing that only backs product families) | Reviewers |
| `judge.json` | The LLM judge's answers, cached by pair and prompt | `python -m tools.f2 judge --send` |

A `matching.json` decision lists groups of records: `same` joins all of them; `different` and `unsure` keep every record of one group apart from the others (`unsure` means reviewed without enough evidence, so the pair is not asked again). Reviewed decisions always win over rules and the judge; an edge that would join two records that must stay apart is not applied and is reported.

Rules by kind, briefly: innovations and offerings are separated by rules and queued when unclear; businesses merge on the same name core (the name without generic words, places and group numbers) in the same place, or a distinctive name with no place conflict; people merge only on an exact normalised full name with a compatible institution or shared work (names are never sent to the LLM); activities and cultural records use deterministic matching. The rules are documented at the top of each `tools/f2/resolve/<kind>.py`.

### The LLM judge

`python -m tools.f2 judge` lists the requests it would send for queued innovation and offering pairs, at no cost. `--send` sends them (needs `OPENROUTER_API_KEY` in the environment; `--budget` stops the run at that many USD; `--entity` limits the kinds). Rules that must not be relaxed:

- Requests go to a zero-data-retention provider with data collection denied.
- Personal names, e-mail addresses and phone numbers are masked before sending; a request that still contains a known full name is not sent.
- Only the answer kinds listed in `judge.APPLIED` (currently: innovations, *different* with high confidence) are applied automatically. Every other answer is a proposal kept on the pair (`match_pairs.judge`) for a reviewer.

Paid runs need the owner's approval.

## Publishing

1. **Build a candidate:** `python -m tools.f2 publish`. It writes `data/runtime/f2/publish/<time>/`, laid out like the repository:
   - `data/public/f2/`: overview, geography, one file per topic and size-bounded detail files;
   - `config/publication_contracts/f2_dashboard.json`: the F2 publication contract regenerated for these files (file list, record counts, allowed name/place fields, measure formulas from `config.json`);
   - `data/public/serving_manifest.json` with the F2 entries replaced, and a new receipt;
   - every other public file and contract (hard links), so the repository's own publication check runs on the complete candidate. The result is in `validation.json`.
2. **Read the diff report** `diff/diff.md` (values, provinces, counted entities, details, structure) against the published files. Explain every change.
3. **Owner sign-off.** The owner approves the candidate as the next public data. Nothing public changes before this.
4. **Promote:** `python -m tools.f2 publish --promote <candidate>`. It copies `data/public/f2`, the contract and the serving manifest into the repository, marks the F2 manifest approved, rewrites the receipt and validates the whole public workspace.
5. **Check and commit:** run `python -m app.cli check`, then commit the release (public files, contract, serving manifest, receipt) on a feature branch and open a PR. Pushing and deploying follow the [publication workflow](publication-workflow.md).

Entity IDs (`inn_…`, `per_…`, `op_…`, `fam_…`, `cul_…`, `act_…`) are derived from the entity's smallest source record key `(source, record_id)`, so they stay the same across refreshes unless that record disappears or a smaller one joins the entity. Saved detail links (`?f2detail=<id>`) therefore usually keep working.

What the publisher guarantees:

- Only fields the dashboard shows are written, and only kinds of fields that were public before. Adding a new kind of field needs the owner's approval.
- Free text goes through the repository's contact redaction (`app/privacy.py`); a text the publication check (`app/publication.py`) would still flag, such as an address, a labelled contact or a person's health or money details, is not shown. A name that cannot be shown appears as *Title withheld pending review*.
- Links must pass the publication check's URL rules and belong to their source; media are references only and are never fetched or hosted.
- A few names that the privacy check would mistake for an address or a contact were reviewed as public (historic houses named by their house number, an innovation named after its LINE channel). They are listed by source record in `config.json` (`reviewed_labels`); the publisher adds a field context to the contract for each.

## Measures and filter semantics

The current scope is 21 measures. Their names, units, formulas, statuses and limitations are in `tools/f2/publish/config.json`; their counting rules are in `tools/f2/measure/`. Current values are on the dashboard and in `data/public/f2/overview.json`.

| Measure | What it counts | Supported selection / limitation |
|---|---|---|
| K01A | Provinces with programme evidence of any kind | Province; institution-only addresses do not count |
| K01B | Cultural areas (AtLocal programme areas and Cultural Map cultural spaces) | Province |
| K02 | Innovators as PMUA reports them | Province and source level; a source total, no person list |
| C02_COMMUNITY | People with a community-innovator or inventor role | Source-reported innovator province; not reconciled to K02 |
| K03 | Reported activity occurrences | Province of the venues; not proof of completion |
| K04 | Innovations with a readiness level of 8 or 9 | Province where the innovation is used |
| C04_LISTED | All listed innovations | Province; K04 is a subset |
| K05 | Businesses and operators | Province; partial coverage |
| K06 | Deferred | — |
| K07 | Product families (ordinary variants of one product count once) | Province |
| K08 | Deferred | — |
| C08_PARTICIPATING | Businesses in the Learning area-based directory | Province; participation is not improvement |
| C08_REPORTED_BUSINESSES | Businesses the Learning dashboard reports | One source breakdown at a time; no cross-tab |
| C08_ASSESSED_PEOPLE | People with a complete development assessment | National only |
| C08_INCREASED_PEOPLE | Assessed people with at least one higher score | National only; a subset of the assessed |
| K09 | Local employment the Learning dashboard reports | Source region only |
| K10 | Money paid to local workers and suppliers | Source region and component; million THB per month |
| C10_ALTERNATIVE | The alternative reading behind the old income figure | Source region and component; never add to K10 |
| K11A, K11B | Unavailable: no supported cluster evidence | — |
| K12 | Cultural Map subjects, including people and knowledge holders | Province and category |

Rules the results follow:

- There is no year or month filter. Fiscal or project years are context; a capture date is not a price date and does not prove current availability.
- A measure answers only the filters in its `supported_filters` and `permitted_combinations`. An unsupported filter returns *unavailable* with a reason, never a borrowed national value; national or source-region values may be shown next to it, labelled as context.
- Entities are counted once after joining. An entity with places in two provinces counts in each province and once nationally, so province values are not additive. Entities without a place count only nationally.
- Zero, unknown and unavailable differ. A province the source does not report is unavailable, not zero.
- Learning dashboard source regions are a separate scheme from provinces and dashboard regions.
- A source total is added up within one breakdown only: the four Learning business breakdowns are four views of one total, not four totals.
- Money uses decimal arithmetic; the display is rounded, the exact value is kept.

## Public files

`data/public/f2/` holds `overview.json`, `geography.json`, 14 `topics/k*.json`, size-bounded `details/<topic>-NNN.json` and `manifest.json`. All are declared in the manifest, the serving manifest and the publication contract.

- **Overview:** every headline with its companions: definition text, national result, coverage and filter contract.
- **Geography:** the 77 provinces with every measure's result, coverage and labelled context.
- **Topic:** `filter_contracts`, precomputed `scopes` (national, each province and, where supported, each source region) with results, filter choices and selections, `items_by_id`, `item_ids_by_measure_and_scope`, and either `details_by_id` or `detail_artifacts` pointing at the detail file.
- **Result:** numeric `value` or null, `display_value`, `unit`, `status`, `availability`, `requested_filters` / `applied_filters` and an `unavailable_reason`. Consumers must not parse display strings or count list items to get a value.

| Detail records | Contents |
|---|---|
| K01B areas, K12 subjects | Name, history/identity text, categories, places, Cultural Map record link and dates, image references |
| K04 / C04 innovations | Title, description sections, readiness by source, use places, organizations, work attributions, catalogue link |
| C02 people | Name, qualifying roles, source-reported innovator province (province only), linked innovations |
| K05 businesses | Name, reviewed source quotes, own place, products it offers, sources it appears in |
| C08 businesses | Directory name, participations (project, fiscal year, research unit), place |
| K07 families | Family name and every offering in it: listings, descriptions, places, prices, sellers, image references, linked innovations |
| K03 activities | Name, dates, venues, publications with links, image references |

Prices are what the source reports, per offering. A reported 0 is shown as *price unspecified/source reports 0*, never as free; AtLocal's placeholder 99999 likewise as *price unspecified/source reports 99999*. Street addresses, coordinates, contacts, account IDs and individual assessments are never published.

## API and dashboard

The serving layer reads only the published files (through `PublicArtifact`). Nothing is fetched, resolved or recomputed at startup or request time.

| Route under `/api/public/v1/f2` | Behavior |
|---|---|
| `GET /overview` | National or `province=<code>` results, with explicit unavailable results |
| `GET /map?measure=<id>` | Province cells and legend for a province-supported measure |
| `GET /topics/{topic_id}` | Result, filters, provenance and a page of items for the selected measure and scope |
| `GET /topics/{topic_id}/details/{entity_id}?measure=<id>` | One detail record that belongs to the measure and scope |

Query parameters, where the route and measure support them: `province`, `category`, `source_level`, `source_region`, `component`, `source_dimension`, `q`, `sort`, `limit`, `offset`, `revision`.

- Lists default to 25 items, at most 100. Search matches item labels only. The KPI `result` is never recomputed from the list.
- Responses carry the revision (the manifest hash); passing `revision` prevents mixing releases. Unknown or non-member entities return 404, invalid filters 422, a stale revision 409, missing or inconsistent published data 503.
- ETags vary by revision and request; responses revalidate (`public, max-age=0, must-revalidate`).

The dashboard has three tabs: **ภาพรวม**, **รายการ**, **ที่มาและข้อจำกัด**. Measure, scope, filters, search, page and the open detail are kept in the URL. Media are links only; nothing is loaded automatically.

## Verification and troubleshooting

Before a PR, run the full gate:

```bash
python -m app.cli check
```

It runs compile, pipeline validation, publication validation, the public-repository boundary check and pytest. `--skip-tests` is a quicker intermediate check.

| Change | Relevant checks |
|---|---|
| Publication/privacy rules | `tests/test_publication.py`, `tests/test_field_contexts.py`, `tests/test_public_artifacts.py` |
| F2 API, filters, revisions | `tests/test_f2_api.py`, `tests/test_f2_c02_api_contract.py` |
| F2 presentation | `tests/test_f2_detail_presentation.py`, `tests/test_ui_coverage.py`, plus a browser check |

`tests/test_f2_api.py` runs against the published files and checks that the API serves what they say (results, coverage, lists, breakdowns, details), plus relationships that hold for any release. It pins no data values, so a release needs no test edits. It does need one zero-price K07 detail and one withheld-title K12 detail to exist; if a release has neither, the test says so.

| Symptom | What to do |
|---|---|
| `no raw snapshot under …` | Put the source's run folder under `data/runtime/f2/raw/<source_id>/` |
| Resolve reports decision issues | Read `decision_issues`: a decision's records disappeared or two decisions contradict each other; fix the decision, not the rule |
| A measure changed unexpectedly | Compare `measure_members` with the published item lists; find the records that moved and why |
| `validation.json` is invalid | Read its problems; fix the publisher or the data. Do not loosen the publication check |
| A file is over its size limit | The publisher stops; detail files are split at about 3.9 MB, topics may not exceed 8 MiB |
| The local server fails at startup | Check the database settings and that the F2 manifest, serving manifest, receipt and contract belong together (run `python -m app.cli check`) |
